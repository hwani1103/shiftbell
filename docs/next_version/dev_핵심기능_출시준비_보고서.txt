2. 이번 수정: 변경 이유·효과·영향·리스크

FIX-01. 가변 스누즈의 실제 선택 분 저장 및 이력 표시
상태: 구현 완료, 필수 검증 결과는 3절에 확정 기록한다.
문제/재현:
- 전역 기본5/10/15와 회차 임시5~30이 실제 예약에 적용되는데 AlarmHistory.dismissLabel은 dismissSnoozed5Min을 항상 사용했다.
- Native 이력에는 snooze_count만 있고 선택한 분이 없어 앱 이력·백업에서 당시 선택을 복구할 수 없었다. 현재 기본값을 읽어 과거 표시를 바꾸는 것도 잘못이다.
수정:
- DB29: alarm_history.snooze_minutes nullable INTEGER. null 또는5/10/15/20/25/30만 허용한다. migrations.json에 v29만 추가하고 repair/신규 설치 구조와 Dart version/Native DATABASE_VERSION을29로 맞췄다. 과거 migrations 및 v28 기대 파일은 보존했다.
- RingSnoozeController는 버튼이 갖고 있던 immutable snapshot의 minutes를 snoozeAt에 전달한다. legacy snooze(minutes)도 전달한다. snoozeAt 직접 호출의 기존 DB/OS 시험은 전달 없는 null을 허용한다.
- 예약 갱신과 이력 insert는 기존 동일 transaction에서 이루어진다. 소모 상태·알람 ID·타입·target epoch·DB commit 후 OS 반영 순서는 유지한다.
- AlarmHistory는 저장된 분을 표시한다. ko/en/de/pt/hi 공통 문자열 dismissSnoozedMinutes(minutes)와 dismissSnoozedUnknown을 추가했다. 기존 공통 dismissSnoozed5Min은 삭제하지 않았다.
- 옛 기록에 없는 값을 추정하지 않는다. null은 일반 '연장/Snoozed/…'로 표시한다. 정식 구버전은5분이었지만 가변 스누즈 dev 기록도 섞일 수 있어 모두5분으로 역산하지 않았다.
효과:
- +15를 실행한 이력은 현재 기본값을5/10/15로 바꿔도15분으로 유지된다. 오래된 버튼 snapshot이15이고 현재 화면이30인 경우에도 실행값15를 기록한다.
- 실행되지 않은 충돌은 기존 충돌 결과로 남아 성공 스누즈 분으로 오인하지 않는다. OS 예약 실패/미검증의 기존 분류는 그대로다.
주요 파일:
- assets/db/migrations.json
- lib/services/database_service.dart, lib/models/alarm_history.dart
- android/app/src/main/kotlin/com/hwani1103/shiftbell/{DatabaseHelper,AlarmActionHelper,RingSnoozeController}.kt
- lib/l10n/app_{ko,en,de,pt,hi}.arb (생성 파일은 생성기 소유)
리스크/한계:
- 영향은 작다고 단정하지 않는다. 새 DB 컬럼은 시작·Native 먼저 열기·백업/복원·잠금 알람의 공통 저장 경로에 걸린다. 변경 위험은 중간으로 관리한다.
- DB29 설치 후 DB28 APK만 덮어쓰는 롤백은 금지한다. 새 데이터가 있으면 백업하고 비파괴 후속 수정으로 처리한다. 원본 데이터 없는 초기화를 해결책으로 쓰지 않는다.
- null인 과거 선택 분은 복구할 정보가 없으며 일반 표시가 의도된 호환 동작이다.
- snooze_count는 기존 회차 누적값 계약을 유지한다. 이번 수정은 카운트 계산, 스누즈 시간 산식, 전역값, 권한/FSI/OEM 정책을 다시 설계하지 않는다.
필요한 증거:

-5언어15분 표시와 null 과거 표시.

FIX-02. 스누즈 분의 구·신 백업 호환과 이력 병합
상태: 구현 완료, 검증 결과는 3절.
문제:
- 새 컬럼을 추가하는 것만으로는 잘못된 백업 분값이 들어오거나, 같은 이력의 기존 null 행이 최신 백업15분을 무시할 수 있다.
수정/효과:
- BackupValidator가 non-null 분값의 정수/허용 범위를 사전에 검증한다. 잘못된 값은 OS 취소·DB 교체 전에 거부한다.
- export의 기존 테이블 자동 수집이 분값을 포함한다. 새 전용 백업 형식을 만들지 않는다.
- RestoreCoordinator의 기존 이력 자연키 병합을 유지하고, 같은 이력에서 기존 snooze_minutes가null이며 새 백업에 값이 있으면 보강한다.
- 기존 known15를 구 백업의 누락/null이 덮지 않는다. 반복 복원은 이력 중복을 만들지 않는다. 구 백업·구 이력에는 값이 없을 수 있다.
- 소비 상태 JSON tuple 키 및 fixed_slot_time 보강 정책은 그대로다.
리스크/한계:
- 같은 자연키의 두 known 값이 다르면 기존 이력 값을 유지한다. 이력이 실제 사실이므로 값이 있는 행을 백업이 임의로 덮지 않는다.
- 신 백업은 구 앱의 컬럼 검증에서 거부될 수 있다. 새 앱에서 구 백업 복원은 지원하지만 DB29 자료를 구 APK에 맞춰 되돌리는 호환은 제공하지 않는다.
- 호스트 실제 SQLite+플랫폼 채널 mock 검사는 OS 파일 선택기·MediaStore·실제 process kill/resume의 전부를 대신하지 않는다. 새 실기기 복원 UI/중단 재개는 NEXT-04에 남긴다.
