알림 7777 확인에 따른 외부 오버레이 표시 정책 — A11 변경·판단 원장
기준: 2026-10-09 KST / dev debug / 출시 승인과 별개

1. 요청과 구현 범위
잠금해제 상태에서 외부 오버레이 위에 7777의 시스템 팝업까지 겹치는 문제를 줄인다.
팝업이 실제로 그려졌는지는 판단하지 않는다. 시스템에 현재 울림의 7777이 등록돼 있고 앱 알림과 실제 게시 채널이 사용 가능함을 확인한 경우에만 외부 오버레이를 생략한다.
현재 알람 = alarmId와 round. 숫자 7777만 발견하거나 권한만 허용된 것은 성공 조건이 아니다.

제품 변경은 CustomAlarmReceiver.kt의 잠금해제·앱 외부 표시 분기 및 새 RingControlPresence.kt에 한정한다.
NotificationHelper의 최초 게시/FSI·그룹·silent 설정, 채널 생성·선택, 잠금 AlarmActivity 진입, 커버 인계, 알람 예약·소리·종료·스누즈·DB는 바꾸지 않는다.
앱을 직접 열었을 때의 InAppAlarmController도 유지한다. 앱 내부 카드와 알림의 공존까지 제거하는 변경은 이번 범위가 아니다.

2. 선택한 판단
기존 최초 게시 후 500ms 지연 시점에서, 잠금해제·외부 overlay 권한 있음일 때만 관찰한다.
- PRESENT: 앱 알림 허용, 활성 알림의 id=7777/tag=shiftbell:ring:<id>:<round>/extra의 alarmId·round 일치, 실제 게시 채널 허용, 그룹이 있으면 그룹 차단 없음 → 외부 overlay 생략.
- ABSENT: 현재 회차 알림을 찾지 못함 → 기존 overlay 유지.
- BLOCKED: 앱 알림 또는 실제 채널/그룹 차단 확인 → 기존 overlay 유지.
- UNKNOWN: 조회 예외, 존재해야 할 채널/그룹 누락 또는 중요도 확인 불가 → 기존 overlay 유지.
API24/25는 채널 없음이 정상이다. API26+에서는 실제 게시 채널을 조회하므로 alarm_control legacy fallback도 판단 대상이다.
API28+의 채널 그룹 차단도 구분한다. HIGH를 필수로 요구하지 않으므로 LOW/MIN의 알림창 제어도 허용한다.
외부 overlay 권한이 없으면 기존처럼 게시된 알림 및 사용자가 앱을 열었을 때의 내부 제어 경로를 유지한다.
잠금 상태 또는 이미 AlarmActivity가 표시된 경우에는 이 새 관찰로 경로를 대체하지 않는다.

3. 이 방식으로 결정한 이유와 대안
과거 7777은 알람을 끄지 않고 홈으로 나왔을 때 남기는 제어 수단이었다. 15a48ad(2026-09-14)는 울리는 즉시 유지형 제어 알림을 게시하도록 넓혔다.
9331959(2026-10-07)에 포함된 제조사 FSI 수정은 최초 알림의 silent/group 동작과 최초/갱신 토큰을 정리했다. 9/14를 현재 팝업이 처음 실기기에 나타난 날짜라고 단정하지 않는다.
현 코드에는 강화된 알림 경로와 기존 잠금해제 overlay 경로가 함께 남아 있었다. 둘이 같은 alarmId/round를 제어하며, 팝업과 알림창 7777도 같은 알림의 표현이다.
7777이 다른 수정 때문에 완전히 불필요해진 잔재라는 근거는 없다. 현재도 FSI 진입 및 화면 이탈 후 제어를 맡는다.

검토한 대안:
- 7777을 조용하게 바꾸기: 원하는 overlay+알림창 UX에 가깝지만, 제조사에서 검증한 최초 알림/FSI 구성을 다시 바꾸는 위험이 있다.
- 7777을 원래 홈 이탈 때만 게시: 최초 FSI와 실패 시 제어를 함께 건드려 범위가 더 커진다.
- 팝업을 작은 떠다니는 아이콘으로 바꾸기: OS 헤드업 알림을 자유로운 앱 아이콘 창처럼 바꿀 수 없으며 별도 UI와 생명주기 설계가 필요하다.
- 외부 overlay 무조건 삭제: 알림 차단·게시 실패 때 자동으로 보이는 제어 수단도 잃는다.
- 앱 알림 권한만 보고 overlay 생략: 채널 차단이나 실제 게시 실패를 놓칠 수 있다.
- 채택: 실제 현재 회차 7777과 게시 채널을 확인하고 외부 overlay만 조건부 생략. 제조사에서 검증한 7777/FSI를 유지하는 데 중점을 둔다.

4. 장점과 수용하는 trade-off
장점: 정상 게시 때 두 외부 제어창이 겹치지 않는다. 알림 차단·부재·확인 실패에는 기존 overlay를 남긴다. 기존 잠금/커버/예약/스누즈 경로의 변경을 피한다. 로그로 PRESENT/ABSENT/BLOCKED/UNKNOWN을 구분할 수 있다.
trade-off:
- 활성 알림 등록은 팝업 표시 또는 알림창에서의 가시성 보장이 아니다. 팝업이 억제되면 사용자가 알림창을 내려 제어해야 할 수 있다. 방해금지 등 표시 제한도 남는다.
- 한 시점의 확인이다. 이후 알림 삭제·권한 철회를 계속 감시하거나 overlay를 자동 재생성하지 않는다.
- 게시가 기존 500ms보다 늦거나 확인에 실패하면 안전하게 overlay를 남긴다. 이후 알림이 표시되면 중복이 생길 가능성을 완전히 없애지는 않는다. 중복 회피보다 제어 수단 보존을 우선한 경계다.
- 앱 내부 카드/커버는 기존 정책이며 전 화면에서 알림과 제어 UI가 하나만 남는 설계가 아니다.
- 사용자 예상 '잠금해제 중 95% 이상 팝업 표시'는 실측 통계가 아니다. 설계·출시 보장 수치로 쓰지 않는다.
