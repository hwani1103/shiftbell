1. 검토 범위와 근거 수준
사용자 요청: UI/UX/인터페이스/디자인 전면 개편, 주요 기능 보존, 일정관리/수면회복 제외. 이번 검토는 소스·현행 제품 계약·기존 광고 준비문서와 Apple/Google/한국 App Store 공개 자료 대조다. 경쟁 앱 구매/실기기 조작/잠금 알람 비교는 하지 않았다. 설명에 기재된 편의성과 실제 동작 성공은 구분한다. 앱스토어 전수 총개수·다운로드·MAU·매출은 확인 불가. 아래 11종은 확인 표본이며 전체 시장 개수가 아니다. 가격은 공개 상품 목록이고 구형/할인 상품을 포함할 수 있어 실제 계정 결제 화면과 다를 수 있다.
기존 원장/PASS/출시 체크리스트/제품 코드를 수정하지 않았다. 신규 검토 원장으로 보존한다. 빌드나 실기기 PASS를 새로 기록하지 않았다. 제품/P0/언어 구조 변경이 없어 critical 실행기 및 release 빌드를 실행하지 않았다.

2. 현재 제품과 이식 범위
읽은 기준: docs/next_version/dev_출시전_핵심코어_체크리스트.txt, 교대시계_최신문서.txt, GoogleAds_UAC_출시준비_검토_2026-10-11.txt(11절 최신 상태), pubspec.yaml, lib/models/alarm_type.dart, alarm_template.dart, constants/alarm_limits.dart, services/alarm_service.dart, firebase_options.dart 등.
현행은 Flutter UI/Dart 데이터와 Android Kotlin 네이티브 알람의 결합이다. 루트 ios 폴더가 없고 Firebase iOS 옵션도 UnsupportedError를 던진다. iOS 빌드만 켜면 되는 상태가 아니다.
보존할 핵심: 순환/요일/불규칙 근무표, 개별 날짜 예외, 전체 조 비교, 근무별 최대5개 알람과 전날/당일/다음날, 일반/custom 알람, 건너뛰기/종료 소비 상태/재생성 방지, 스누즈, 다음 알람/이력, 근무 메모/시간·OT 집계, 친구/공개 웹 공유, 백업/복원, 달력 위젯, 테마/현지화. 일정관리/수면회복은 요청에 따라 신제품 범위에서 제외하는 제안이며 현행 Android에서 삭제한 것이 아니다.
달력/근무/템플릿/예외/통계/공유/백업은 iOS 구현 가능 범주. 기존 Dart 계산·검증·DB 의미를 재사용하고 OS 어댑터를 분리하는 것이 권장된다. SQLite를 Flutter와 App Intents/위젯이 함께 접근할 경우 App Group 저장소·동시쓰기·이관/복원 잠금 계약이 필요하다. Android 네이티브 엔진도 계산·소비 처리를 수행하므로 Dart만 옮겨서 기존 계약이 모두 따라온다고 보면 안 된다.

3. iOS 알람 가능성과 주요 제약
AlarmKit은 iOS26 이상에서 시스템 알람/스누즈와 앱별 알람 권한을 제공한다. 이전 iOS의 일반 로컬 알림과 기상 알람의 제품 보장은 다르다. 기상 알람이 핵심이라면 iOS26 이상을 최소 지원선으로 검토한다. 실제 최소 마이너 버전은 실측 후 결정한다.
Android overlay/FSI/알림채널 권한 설계를 복제할 수 없고 iOS 시스템 알람 UI 및 App Intents/Live Activity로 다시 설계해야 한다. 커스텀 소리는 공식 경로가 있지만 앱별 볼륨/진동 강도/진동 전용/완전 무음/자동 종료 길이/잠금 중 즉석 −/+5분의 동일성은 확인된 API만으로 보장할 수 없다. 최신 SDK와 지원 OS에서 각각 기술 검증 후 동일 제공·대체 제공·제공 불가를 명시해야 한다.
가장 큰 구현 위험은 현재의 10일 롤링 예약이다. App Refresh가 매일 지정 시각에 실행된다고 가정할 수 없다. 주 단위 반복은 지원하더라도 임의 40칸 교대 주기와 날짜 예외가 주간 반복으로 자동 표현되지는 않는다. 개별 날짜 예약, 용량 확인, 사용자의 명시적 조작 때 갱신, 불확실한 상태 안내가 필요하다. AlarmKit maximumLimitReached 오류가 존재하지만 검토한 공식 자료에서 보편적인 숫자 한도를 확정하지 못했다. 일반 로컬 알림의 한도를 AlarmKit 한도로 옮기지 않는다.
수개월 달력 계산 가능과 그 기간 알람의 OS 등록 완료는 다른 상태다. 매일 앱을 열라는 조건이 핵심 신뢰성의 전제라면 자동 교대알람 제품으로 출시할 타당성이 약해진다. 등록된 시스템 알람 자체와 미래 예약을 앱이 보충하는 작업도 분리해 평가한다.
스누즈5/10/15분과 실제 회차5~30분 조절, 충돌 시 기존 예약 유지, 종료 슬롯 비부활, 시차/DST, DB 성공/OS 실패 구분, 복원·재설치 뒤 권한 확인은 iOS 기술검증 인수 조건이다. 설정을 열었다는 이유로 권한 허용을 표시하지 않는다.
AlarmKit의 공식 기능 존재를 기기 전체 안정성 PASS로 취급하지 않는다. Apple 개발자 포럼에도 지연/커스텀 사운드 문제의 사용자 보고가 있으나, 이를 모든 최신 OS의 확정 결함으로 확대하지 않는다.

5. 제품과 UI/UX 개편 제안
핵심 약속: 근무표를 바꾸면 필요한 기상 알람도 같이 바뀌고, 사용자가 다음 울림을 바로 확인할 수 있다.
기능 개수는 보존하되 탐색 구조는 오늘/달력/설정의3개 축을 우선 검토한다. 오늘에는 다음 근무·다음 알람·예외·등록 확인을 배치. 달력에는 월/주·전체 조 전환과 날짜 시트. 설정에는 근무 규칙·근무별 알람·외형·공유·백업을 명확한 그룹으로 둔다. 현재 모든 세부 화면을 새 탭으로 복제하지 않는다.
기상 화면에 광고·평가 요청을 놓지 않는 제안. 차분한 기본 팔레트/근무색/명확한 대비, 라이트·다크, 큰 글자·VoiceOver·색 외의 근무 표식, 손가락 접근 가능한 핵심 버튼이 우선이다. 시각효과는 상태 이해와 성능을 해치지 않는 범위로 사용한다.
근무 설정에서 기준일+패턴 입력 →14일 미리보기 →근무별 알람 →7일 실제 예약 결과 확인. 요청 권한은 필요한 시점에 하나씩 처리한다.
차별화 후보는 수정 전후 미리보기: '12일 야간→휴무, 관련 알람2개 취소', 단일 예외의 되돌리기, 전날/다음날 알람의 실제 울림 날짜 표시, 달력 저장/OS 등록/권한 미허용/확인불가 상태 구분이다. OS가 확인하지 못한 배터리/볼륨 등을 통과했다고 녹색 배지로 표현하지 않는다.
교대별5개·전후날·조비교는 현행 자산이지만 경쟁의 제공 불가를 조사 없이 주장하지 않는다. UX 우위는 실제 근무자 과업 비교로 검증한다. 모든 코드를 버리는 것과 UI 전면 개편은 별개이며 기존 검증된 규칙의 재사용을 권한다.
Flutter UI+Swift AlarmKit/App Intents/WidgetKit 권장. SwiftUI 전체 신규 작성은 완전한 Apple 전용 전략을 선택할 때 대안이며 두 플랫폼 기능 로직의 장기 중복 유지비가 늘 수 있다.

6. 비용과 수익 모델
사용자 제시150만원을 iOS 초기 현금 하한으로 비교한다. 중고 장비 실거래 견적을 이번에 확인하지 않았으므로 특정 Mac/iPhone의 현 시세라고 제시하지 않는다. MacBook 자체는 필수가 아니므로 이동 개발 필요가 없으면 Mac mini+기존 주변기기도 비교할 수 있다. 구입 모델은 최신 제출용 Xcode/macOS와 목표 iOS를 지원하는지 공식 요구사항으로 확인해야 한다. 중고 초기화/소유권 잠금/배터리·수리비·향후 지원기간은 구매 때 확인한다.
Developer Program은 연99달러(한국 실제 결제가는 결제 시 확인)이며 매년 비용. 개발자의 작업시간, 실기기·OS 조합 검증, 마이너 버전 유지보수, 출시 후 사용자 확보비는150만원에 자동 포함되지 않는다. 한 기기에서 모든 모델/버전 PASS를 얻을 수 없다.
개발 기간은 계획 가정: 기술 시제품1~2주, 핵심/새 UX6~10주, 베타·복구·시간대·스토어2~4주. 겹치는 작업과 경험에 따라 크게 달라져 합계 약2~4개월을 일정 여유로 가정하되 확정 견적이 아님.
수익 예시(시장 실적 아님): 연14,000원 상품, Small Business Program 승인 후15% 수수료만 단순 반영하면11,900원.150만원 회수에는 약127건 결제가 필요. 세금/환불/서버/광고/노동비 제외이므로 실제 목표는 더 높아짐. 유료 전환2% 가정이면 약6,350설치,5%면 약2,540설치가 필요하다. 일반30% 수수료 단순 시 약154건. iOS 사용자가 결제를 많이 한다는 일반론만으로 이 앱 전환율을 정하지 않는다.
광고만으로 회수하는 예: 활성사용자 월 순기여100원/300원/500원,12개월 동일 활동 가정이면150만원 회수에 각각1,250/417/250명. 실제 이탈·초기 사용자 확대·개발비는 제외. eCPM만 보지 말고 노출 횟수/광고 허용/실제 유지기간을 반영한다. 알람만 쓰는 사용자에게 배너 수익이 자동 발생하지 않는다.
무료 핵심/광고제거·표현·공유 편의 유료를 첫 후보로 고려하되, 공유도 핵심을 전부 제공하려는 요구라면 무료 핵심 범위를 먼저 합의해야 한다. 기존 핵심 기능을 유료로 옮기는 결정을 이번 검토가 승인한 것은 아니다.

7. Android UAC와 비교
이미 존재하는 제품을 검증할 수 있어 UAC는 수일~수주 내 수요/이탈 학습이 가능. iOS 본개발은 신규 사용자 시장과 장비 자산을 얻는 대신 출시 지연·OS 어댑터·두 플랫폼 유지비가 생김. 광고비는 쓰면 대부분 소진되며 장비는 재판매 가치가 있을 수 있으나 확인된 잔존가를 가정하지 않는다.
기존 광고 준비문서11절상 GA4/Firebase→Ads 연결과 prod onboarding_complete 보조 전환 준비는 완료. 결제·설치/first_open 전환·최종 주목표 및 prod 동의 런타임 확인은 잔여. 이번 세션에서 콘솔을 다시 검증하거나 광고를 집행하지 않았다.
150만원 전액 즉시 집행은 비추천. 예시 배분: 국내 단일 캠페인 50~70만원/10~14일1차 →잔존·활성화·수익 평가 →추가30~50만원 또는 중단, 잔액은 유보. 일예산은 실제 CPI와 Google 권고에 맞춰 재계산한다. Google은 설치 최적화 일예산≥목표CPI50배, 인앱 행동≥목표CPA10~15배와 학습7~14일을 권고한다. 필수 집행 요건이나 보장 수익은 아니다. CPI1,000원을 목표로 잡는 가정이면 일5만원×14일70만원이 규모 예시. 단기 소액 여러 국가 분산은 표본과 학습을 약화시킬 수 있다.
150만원 가상 결과(예측 아님): CPI500원/1,000원/2,000원 →3,000/1,500/750설치. 온보딩60%, 그중D7활성40%를 가정하면720/360/180명, D7활성1명당 약2,083/4,167/8,333원. 실제 D7활성은 앱을 다시 여는 사용자 기준으로 알람 전용 유지자를 누락할 수 있다.
판정 기준: CPI가 아니라 신규 광고 유입의 초기 설정 완료·D7/주간 유지·D30·실제 순수익 기여. 설치당 기대 순기여보다 CPI가 크면 수익 확보 목적 확대는 정당화하기 어렵다. 광고 중단 후 자연 유입 증가는 별도 관측하며 광고가 검색 순위를 올렸다는 인과나 자동 선순환을 보장하지 않는다. 기능 결함/낮은 유지율이면 광고 중단 후 원인 개선, CPI가 너무 높으면 소재·대상·채널 문제도 분리한다.

8. 추천 실행 순서와 iOS 재판정 조건
(1) 현행 Android 출시/측정 잔여 마무리, 자연 유입의 유지·수익 기준선 확인.
(2) 단일 시장 UAC 1차 실험, 사용자가 정한 손실 한도 내 진행. D7 뒤 의사결정하고 D30 수익까지 계속 관측.
(3) 동시에 비공개 디자인 과업/실제 근무자 인터뷰로 iPhone 수요와 경쟁 앱 대비 불편 확인. iPhone 교대근무자15~20명의 구체 근무표 사례, 그중 베타10명 확보는 추천 모집 목표이지 통계적 시장검증 기준이 아님.
(4) 빌리거나 저비용 접근한 Mac/아이폰으로 AlarmKit 시제품. 잠금/무음/집중/장기 미실행/재부팅 전후/권한 철회/스누즈/충돌/최대템플릿/오프셋/시간대/DST/백업 복원 인수 조건 확인. 무료 개발 계정의 프로비저닝 기간은 장기 미실행 검사에 영향을 줄 수 있어 검증 목적에 적절한 서명을 확보한다.
(5) 기술 제약 수용, 구체 수요, 유료/광고 회수 경로, 양 플랫폼 유지 시간의 네 조건을 충족하면150만원 이상 장비/개발 투자. Android UAC 실패는 iOS 성공·실패를 직접 증명하지 않으며 별도 iPhone 수요가 강하면 iOS 소규모 기술검증을 계속한다.
최종 의견: iOS는 중장기 출시 후보로 가치가 있지만 현재 즉시 전면 개발을 시작할 근거는 부족하다. Android의 사용과 획득 경제성을 먼저 제한된 예산으로 확인하는 편이 현재 선택의 불확실성을 더 빨리 줄인다. UI 혁신은 알람 관련 실수를 줄이고 예약 결과를 이해시키는 방향으로 정의해야 한다.
