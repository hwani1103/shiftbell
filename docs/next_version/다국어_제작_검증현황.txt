5. 번역 품질을 높이기 위한 반복 검토 제안 — 2026-10-05
사용자 제안: 새 세션마다 독립적으로 문구를 검토하고, 실제 사용 근거와 변경 이력을 남겨 다음 세션에서 개선한다.
아래는 권장 운영안이다. 이 절을 추가했다고 새로 4개 언어 전수 감수나 현지인 검수를 수행한 것은 아니다.

권장 순서
1) 언어별 기준 고정: 영어는 공통으로 통하는 표현과 필요한 미국/영국 차이를 구분하고, 독일어는 독일, 포르투갈어는 브라질, 힌디어는 인도의 힌디어 사용자를 대상으로 한다. 힌디어를 인도의 모든 사용자가 쓰는 언어로 간주하지 않는다. 호칭·말투·대소문자·버튼 어투·허용 약어를 기록한다.
2) 화면 단위 의미 카드: 문자열 키, 실제 기능, 표시/실패 조건, 누르면 일어나는 일, 연결되는 버튼·도움말, 예시 변수값, 길이 제약을 함께 본다. 한국어 원문에도 모호함이 있으면 코드 동작부터 확인한다. 영어 번역을 다른 언어의 유일한 원문으로 삼지 않는다.
3) 독립 검토: 한 번에 한 언어·한 흐름(예: 온보딩→근무 생성)을 다룬다. 첫 판단은 기존 수정 사유를 읽기 전에 적되 기능 설명과 용어 기준은 제공한다. 실제 사용자가 무엇을 이해할지, 오역/모호함/부자연스러움/불일치가 있는지를 찾는다. 수정 개수를 목표로 삼지 않는다.
4) 근거 대조: 후보 작성 후 이전 이력과 대조한다. 단순 선호 차이는 유지한다. 되돌리려면 이전 근거를 왜 기각하는지 기록한다. 독립 세션의 의견 일치를 현지인 검증으로 계산하지 않는다.
5) 제한된 반영: 의미 오류와 위험한 안내를 먼저 고친다. 기본 근무명, 근무/휴무/휴가/초과근무 같은 핵심 개념은 용어표를 기준으로 연결된 버튼·알림·도움말을 함께 확인한다. 문법에 따른 활용형까지 기계적으로 동일 문자열로 강제하지 않는다.
6) 검증: 변수·복수형·키 누락·원치 않는 원문 잔존·Android/Flutter 용어 일치를 자동 검사한다. 이후 별도 화면 단계에서 배율·줄바꿈·결합 문자·잘림을 확인한다. 자연스러움은 자동 테스트 통과만으로 판정하지 않는다.
7) 최종 사용자 검토: 가능하면 해당 언어로 일하는 교대근무자가 실제 화면에서 할 일을 수행하게 하고, 버튼의 의미·결과를 본인 말로 설명하게 한다. ‘자연스러운가요?’ 질문만으로 끝내지 않는다.

근거 수집 기준
- Android/Google 등 공식 현지화 UI: 알람·권한·백업 같은 시스템 동작의 용어 참고.
- 현지 병원·사업장·교대 일정 서비스의 원문: 실제 근무 용어와 직종 범위 참고.
- 커뮤니티·사용자 대화: 구어적 자연스러움과 약어 이해도 참고. 한 직종이나 한 게시글의 용례를 국가 전체로 확대하지 않는다.
- 책·사전: 정확한 의미와 문법 참고. 학술/행정 표현이 짧은 앱 버튼에도 적절한지는 별도로 판단한다.
- 출처는 URL 또는 서지정보, 확인일, 실제 사용 문맥, 후보를 지지하는 이유를 남긴다. 열람하지 못한 자료는 확인된 근거로 쓰지 않는다.
- 핵심 용어는 가능하면 독립된 두 종류의 근거를 대조한다. 검색 결과 수나 단일 유명 앱의 표현만으로 채택하지 않는다.
- 역번역은 의미 누락을 찾는 보조 도구다. 역번역이 같다는 이유만으로 자연스러운 번역이라고 판정하지 않는다.

문구 변경 이력 필드(기존 원장 CSV와 연결; 긴 출처 원문 전체를 복사하지 않음)
검토 ID / 날짜 / 기준 커밋 / 언어·지역 / 문자열 키 / 화면·동작 문맥 /
이전 문구 / 제안 문구 / 한국어로 설명한 뜻 / 문제 유형·심각도 /
출처·확인일·사용 문맥 / 기존 결정과의 차이 / 채택·보류·기각 및 이유 /
연결 문구 / 자동검증 결과 / 화면검증 상태 / 반영 커밋

변경하지 않는 결정과 보류 후보도 남긴다. 최신 채택 문구는 ARB/XML, 현재 용어 기준은 용어표, 의사결정 이력은 원장으로 구분한다. 변경 이력은 덮어쓰지 않고 새 검토 ID로 연결한다.
여러 세션을 동시에 열 경우 같은 ARB/XML을 함께 수정하지 않는다. 검토 결과를 별도 파일/브랜치로 제출하고 하나의 반영 단계에서 합친다.
종료 기준 예시: 핵심 흐름의 의미 오류·모순 없음, 필수 용어 통일, 두 차례 검토에서 새로운 중대 문제가 없음. 남은 취향 차이는 동결하고 실제 사용자 피드백으로 재검토한다. 이 기준은 무결함 보증이 아니다.

다음 세션에 전달할 요청 예시
“다국어_제작_검증현황.txt의 검토 절차를 읽고 [언어/흐름]을 검토해줘. 먼저 코드에서 기능 의미와 표시 조건을 확인해. 이전 수정 사유를 읽기 전 독립 후보를 기록하고, 이후 이력 및 실제 현지 사용 근거와 대조해. 단순 취향 차이는 유지하고 의미·자연스러움·일관성이 분명히 좋아지는 변경만 제안해. 키/전후 문구/출처/채택 또는 기각 사유를 남기고, 번역 검증과 레이아웃 검증 상태를 구분해.”
