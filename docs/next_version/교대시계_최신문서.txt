Fold8

7. 실행 도구·촬영 정확도·종료 규칙

연결 전 PC 준비
- 준비 APK가 최신 소스와 일치하면 재빌드하지 않는다. 코드 수정 시 필요 검사 후 빌드: flutter build apk --debug --flavor dev --no-pub
- 단, 과거 결과만 믿고 실패한 빌드를 설치하지 않는다. 실제 파일 SHA256/버전/빌드 시각 기록.
- PC RAM 6GB: 폰 렌더링은 SRTL 기기에서 하지만 Flutter/Gradle/브라우저는 PC RAM을 쓴다.
  빌드 여러 개/브라우저 여러 개/에뮬레이터를 동시에 띄우지 않는다. 기기 연결 시간을 빌드 대기에 쓰지 않는다.

연결 직후
- adb devices -l, 실제 model/OS, wm size/density, font_scale, 상태바/내비게이션/키보드 인셋 기록.
- 충전 중 화면 유지 settings stay_on_while_plugged_in 및 dumpsys power mStayOn/Awake 확인.
- adb -s <새serial> install -r build/app/outputs/flutter-apk/app-dev-debug.apk
- dev 패키지 com.hwani1103.shiftbell.dev만 사용. 최신 dev VM에 attach하고 새 URL/PID를 확인.
- SHIFTBELL_AUDIT_SERIAL / SHIFTBELL_AUDIT_OUT / SHIFTBELL_AUDIT_VM_PORT / SRTL_DEVICE_NAME 지정.
- tools/srtl_current_audit.py fold()와 srtl_web_layouts.mjs는 옛 Ultra의 state 0/3을 하드코딩한다.

8. 기능 원장 판정 원칙과 별도 기능 검증 운영

행에 여러 조건이 있으면 전체를 만족해야 PASS. 일부 증거는 해당 부분 완료로 기록하고 빠진 단계만 남겼다.
이번 UI 수정 후의 최신 APK에서 모든 기능을 재실행했다는 의미가 아니다. 각 증거의 빌드/시점 범위를 보존한다.
이전 도구 usb_oct02_inventory.py/usb_oct03_inventory.py를 무작정 재실행하면 이번 판정을 덮어쓴다.

후속 검증 완료 후 무작정 재실행하면 오늘 기준 상태로 돌아가므로, 후속 결과는 원장에 직접 누적하거나 도구 기준도 함께 갱신한다.
이미 끝낸 수십 개의 검사를 오늘 다시 한 것과, 원래 미완료 행의 마지막 조건을 끝낸 것은 다르다.
특히 다음을 같은 것으로 간주하지 않는다:
- 잠금에서 '소리+진동'만 검사한 것 vs 잠금에서 3종 전부 검사.
- 실제 잠금에서 첫 스누즈 누름 + 5분 후 재울림 vs 재울림 후 잠금 UI의 X까지 전체 동선 완료.
- 같은 ID의 옛 회차 vs 다른 ID A→B 인계의 옛 버튼.
- 내부 Native/receiver 호출 vs 해당 화면을 통한 실제 사용자 조작.
- Fold 커버 vs Flip 커버, 모의 채널 실패 vs 실제 OS 일부 예약 실패.

후속 기능 검증은 별도 예약한다. SRTL 레이아웃 세션에 끼워 넣지 않는다.
날짜/DST 조작·DB 실패 주입·권한/저장 공간 실패는 개인 폰보다 격리 dev/에뮬레이터가 적합하다.
서버/Play/실제 PWA는 운영 조건을 준비한 별도 세션에서 검증한다.
아래 '사용자 직접' 항목만 사용자가 물리 기기에서 확인할 성격이다. 원장 나머지 전체를 사용자에게 떠넘기지 않는다.
가능성 평가는 실제 발생 확률 수치가 아니라 미검증 위험 시나리오다.

9. 사용자 실제 폰에서 직접 확인할 항목 — 다른 기능 잔여와 분리

공통 준비: 실사용 데이터 백업, 방해받지 않는 시간, 테스트 알람 식별, 정상 알람에 영향 없는 별도 회차.
원본 알람/음량/권한/언어/시간대의 변경 전 값을 기록하고 끝나면 복구한다.
자동화 실패 주입이나 휴대폰 저장 공간 강제 고갈은 사용자에게 요구하지 않는다.

[H1 / HUMAN-001] 소리·진동·무음의 실제 체감
방법: 앱 제공 소리와 제조사 소리를 대표적으로 바꾸고, 소리+진동/진동/무음으로 1회씩 울린 뒤 끈다.
원장 '7종'은 실제 현재 선택 목록과 대조한다. 없는 음원을 만들어 검사할 필요는 없다.
의도: 로그상의 ringing과 실제 소리/진동 전달이 일치하는지. 끈 뒤 잔여 재생이 없는지.
위험: 잘못된 오디오 경로/진동 세기/무음에서 뜻밖의 소리/중지 후 재생 지속. SRTL 영상만으로 확정 불가.

[H2 / RING-020] 통화·이어폰·Bluetooth·DND·알람 볼륨0
방법: 평상시 상태와 조건 하나씩 비교. Bluetooth 연결/해제, 유선 이어폰이 있으면 비교,
  DND는 알람 허용 여부를 함께 적고, 볼륨0과 복구 상태를 구분한다. 통화 중에는 동의한 상대와 시험.
의도: 어떤 스피커/이어폰으로 전달되는지, OS 설정과 앱 설정에 맞는 동작인지.
위험: 경로 전환으로 안 들림/원치 않는 큰 소리, 통화 후 오디오 복구 누락. 단순 '안 들림'을 앱 결함으로 단정하지 않는다.

[H3 / HUMAN-002, REFRESH-003] 잠금·유휴·재부팅 첫 잠금해제 전
방법: 가까운 테스트 알람을 만들고 잠금 상태로 대기. 별도로 충분히 유휴 상태에서 확인.
  재부팅 시험은 사용자 동의 시 예약을 남긴 채 재부팅하고 첫 잠금해제 전에 지정 시각을 맞는다.
  기능 로그/DBOS 대조는 다음에 Codex가 함께 확인하며 사용자는 화면·소리·진동 전달을 기록.
의도: 앱을 안 열어도 알람이 실제 깨우는지, Direct Boot 접근이 안전한지.
위험: 잠금 저장소 접근 실패/예약 복구 누락/울림 전달 누락. HUMAN과 REFRESH는 같은 시험 증거를 공동 사용해 중복 대기하지 않는다.

[H4 / HUMAN-003] 비교 원본 캡처·자유 탐색
방법: 전달 갤러리를 원본/화면 맞춤으로 보고 실제 중요 달력에서 긴 근무명·메모·오늘 표시 확인.
의도: 자동 기하 검사로 판단하기 어려운 예쁨·가독성·여백의 독립 평가.
위험: 글자가 너무 작아지거나 기술적으로 안 넘치지만 답답한 구성. 수정 제보는 번호·기기·언어·배율을 함께 전달.

[H5 / HUMAN-004] 바형 S26 영어 확인
방법: 영어로 전환하고 실제 영어 근무명·메모가 있는 상태에서 달력/셀 팝업/알람/설정을 자유 탐색.
의도: 원래 바형 기기에서 폴더블 수정의 부작용이 없는지, 실제 입력 문자열의 가독성.
위험: 긴 영어 축소/줄바꿈/한국어 잔류/키보드·하단 버튼 가림. 한국어 전체 재시험은 요구하지 않는다.

[H6 / HUMAN-005] 배율·시스템 내비게이션 체감
방법: 1.0/1.3, 제스처/3버튼 내비게이션에서 화면 마지막 행과 저장/취소 버튼을 누를 수 있는지.
의도: safe area·시스템 영역 오터치·터치 여유를 실감 기준으로 확인.
위험: 하단 잘림/뒤로가기 오터치/버튼 너무 작음. 검사 후 원래 설정으로 복구.

위 직접확인은 강제 실패/희귀 DST 테스트와 별개다. 실제 Flip을 사용자가 보유하지 않으면
Flip 커버 기능 잔여를 이 목록에 떠넘기지 말고 별도 기기 확보가 필요한 Codex 항목으로 유지한다.

## 1. 버전 올리기

**고쳐야 하는 파일 2개:**

### ① `pubspec.yaml` (프로젝트 최상위 폴더)

```yaml
version: 1.0.23+25
```

`1.0.23` = 버전 이름 (사람이 보는 버전)
`+25` = 버전 코드 (내부 관리용 숫자, 반드시 이전보다 커야 함)

### ② `android/app/build.gradle.kts`

```kotlin
versionCode = 25
versionName = "1.0.23"
```

**⚠️ 이 두 파일의 값은 서로 짝이 맞아야 합니다:**
- `pubspec.yaml`의 `+25` ↔ `build.gradle.kts`의 `versionCode = 25` → **반드시 같은 숫자**
- `pubspec.yaml`의 `1.0.23` ↔ `build.gradle.kts`의 `versionName = "1.0.23"` → **반드시 같은 문자열**

**업데이트할 때 규칙:**
- `versionCode`(=`+숫자`)는 배포 때마다 **무조건 1 이상 증가**. Play Store가 이전 버전보다 작거나 같으면 업로드를 거부함.
- `versionName`(=`X.Y.Z`)은 사람이 보는 숫자라 자유롭게 정하면 됨. 보통 작은 수정/버그 픽스는 마지막 자리(Z)만, 기능 추가는 가운데 자리(Y)를 올림.

**예시 (다음 업데이트가 자잘한 수정이라면):**
```
pubspec.yaml:        version: 1.0.24+26
build.gradle.kts:    versionCode = 26 / versionName = "1.0.24"
```

**참고**: `lib/services/update_service.dart`의 `_releaseNoteVersion`은 Play의 새 버전 안내와 별개인, 업데이트 **후** 첫 실행 안내용 ID입니다. 새 안내를 띄우려면 ID와 한국어·영어 ARB 문구를 함께 바꾸고, 불필요하면 빈 문자열로 둡니다.

**업데이트 가능 안내**는 Firestore 문서가 아니라 Google Play 인앱 업데이트 API가 판단한다. 앱을 시작하거나 다시 열 때 확인하되, 마지막 성공 확인부터 6시간이 안 지났으면 건너뛴다. Play가 해당 계정·기기에 새 버전을 제공하면 **기존의 "새 버전이 있어요" 안내 팝업과 문구**를 그대로 보여준다. 사용자가 "나중에" 또는 "업데이트"를 명시적으로 누르면 그 버전의 팝업은 다시 띄우지 않는다. Play 반영 지연, 앱을 열지 않은 기간, 조회 실패 때문에 안내까지 걸리는 최대 시간은 보장할 수 없다. 따라서 Play 내부 테스트 트랙에서 낮은 버전 설치→높은 버전 공개→앱 재진입을 실제로 검증한다. `app_config/android.latestVersionCode`는 새 앱에서 더 이상 읽지 않지만, 아직 1.0.23을 쓰는 기기는 기존 방식으로 읽으므로 운영 문서를 삭제하지 않는다.

  값을 넣고 다시 빌드하면 됩니다. (예전 설명 "빠뜨리면 수익만 0"은 틀렸음 - 앱 ID만 빠지면 테스트 앱 ID로 실제 배너를 요청하는 상태였음)

## 2. 빨간날(공휴일) 추가·수정: 앱은 Firestore, 웹은 배포

앱은 **기본 날짜 목록 + Firestore 변경분**을 사용한다. 웹 친구 공유 뷰어는 **빌드할 때 포함된 기본 날짜 목록**을 사용한다. 앱용 Firebase 문서를 고쳐도 배포된 웹 파일은 바뀌지 않는다. 앱 홈 위젯은 기본 날짜 목록(Kotlin)에 앱이 읽은 원격 변경분을 적용한다. 한국 공휴일은 한국어 화면에서만 보인다.

### A. 앱에 적용: Firebase 콘솔에서 문서 수정

1. 먼저 공식 발표로 **날짜와 표시 이름**을 확인한다. 아래 `2026-10-07`은 사용법 설명을 위한 가상 사례다.
2. [Firebase 콘솔](https://console.firebase.google.com/)에서 프로젝트 **`shiftbell-29f31`**을 선택한다. **Firestore Database → 데이터**에서 컬렉션 `app_config`, 문서 `holidays_kr`를 차례로 연다. `app_config/android`는 **업데이트 안내용 옛 문서**이므로 공휴일 작업 때 건드리지 않는다.
3. `holidays_kr` 문서가 없으면 `app_config` 컬렉션 안에 문서 ID를 정확히 `holidays_kr`로 만들어 아래 필드를 추가한다. 이미 있으면 **문서를 새로 만들거나 전체를 비우지 말고 해당 필드만 편집**한다.

```text
문서 경로: app_config/holidays_kr
version   Number    1
add       Map
  2026-10-07   String   대체공휴일
remove    Array     []
```

4. **새 빨간날 추가:** `add` 지도(Map) 안에 하위 필드를 추가한다. 하위 필드 이름은 `2026-10-07` 같은 `YYYY-MM-DD` 날짜, 값의 타입은 **String**, 값은 `대체공휴일` 같은 화면 표시 이름이다. 기존 `add`의 다른 날짜는 유지한다. 콘솔에서 저장하면 서버 값은 즉시 바뀌지만 **사용자 앱 반영은 다음 조회 때**다.
5. **이미 있는 날짜의 이름만 수정:** 그 날짜가 `add`에 있으면 값(String)을 편집한다. 기본 목록에만 있다면 같은 날짜를 `add`에 새로 넣고 원하는 이름을 적는다. `add`의 이름이 기본 이름보다 우선한다.
6. **잘못된 날짜 삭제·이동:** 기본 목록의 날짜라면 `remove` 배열에 날짜를 **String 요소**로 추가한다. 다른 날로 옮긴다면 옛 날짜를 `remove`에, 새 날짜와 이름을 `add`에 넣는다. `add`에서만 추가했던 날짜를 취소할 때는 그 항목을 `add`에서 삭제하면 된다. 같은 날짜가 `add`와 `remove`에 모두 있으면 `add`가 우선하므로 중복을 피한다.
7. 편집할 때마다 `version` 숫자를 1 올려 관리 기록으로 쓴다. 앱은 이 숫자를 따로 확인하러 읽지 않으므로, **숫자만 올려서는 즉시 갱신되지 않는다.** `add`와 `remove`는 이번 작업만이 아니라 앞으로 유지할 **변경분 전체**다. 다른 날짜를 실수로 지우지 않았는지 저장 전후 확인한다. 날짜 형식이 틀리면 앱이 그 항목을 버리고, 이름은 최대 20자까지만 사용한다.

앱은 새 방식을 처음 실행할 때 **첫 조회일을 0~7일 사이에 무작위로 저장**한다. 성공적으로 읽으면 **14일 뒤**, 그 이후 앱을 열거나 다시 열 때 다시 읽는다. 실패하면 1~2일 뒤 재시도하고 마지막 성공 결과를 유지한다. 따라서 앱을 계속 쓰는 사용자도 변경 직후 약 14일, 앱을 열지 않으면 그보다 오래 옛 날짜를 볼 수 있다. 이는 하루 정확히 1,000명 제한이 아니며, Firestore 읽기 1회는 친구 공유 등 다른 읽기와 같은 할당량을 사용한다. **급히 모두에게 즉시 보여야 하는 변경에는 적합하지 않다.** 현재 출시판 1.0.23은 `holidays_kr`를 읽지 않으며, 이 방식이 포함된 앱 버전부터 원격 변경을 받는다.

**2030년 이후를 앱 업데이트 없이 추가하려면:** 연도별 기본 목록은 현재 2029년까지다. 2030년의 설날·추석·대체공휴일처럼 연도별 날짜가 공식 확인되면, 해당 연도가 오기 **적어도 몇 주 전**에 날짜별로 `add`에 입력한다. 고정 날짜(`01-01` 등)는 기본 목록이 매년 적용한다. 앱을 업데이트하지 않아도 다음 조회를 마친 앱과 홈 위젯에 2030년 원격 날짜가 반영된다. 다만 앱 달력은 현재 연도 기준 앞뒤 3년만 열리므로, **2026년에는 2030년 화면 자체를 열 수 없고 2027년부터 보인다**(3절 참고). 웹에는 아래 B 절의 별도 배포가 필요하다.

### B. 웹에 적용: VS Code에서 수정·빌드·배포

1. VS Code에서 프로젝트 폴더 `C:\Users\Administrator\Desktop\shiftbell`을 연다. `lib/utils/holiday_util.dart`를 열어 **`lunarHolidays`**(해당 연도만의 날짜, `YYYY-MM-DD`) 또는 **`fixedHolidays`**(매년 같은 날짜, `MM-DD`)를 찾는다. 웹 전용 공휴일 파일은 없다.
2. 해당 연도의 새 날짜는 `lunarHolidays`에 `'2026-10-07': '대체공휴일',`처럼 넣는다. 이름 수정은 기존 항목의 문자열 값을 고치고, 날짜 이동은 옛 항목을 지운 뒤 새 날짜를 넣는다. `fixedHolidays`를 바꾸면 **모든 연도**가 바뀌므로 한 해만의 예외라면 연도별 처리 여부를 먼저 확인한다. 2030년 날짜도 새 `// 2030년` 구역을 만들어 같은 형식으로 넣는다. 저장한다.
3. VS Code 상단 **터미널 → 새 터미널**을 연다. 현재 위치가 프로젝트 루트인지 확인한다. 다른 위치라면 `cd C:\Users\Administrator\Desktop\shiftbell`을 실행한다. 먼저 아래 테스트를 실행한다.

```powershell
flutter test test/holiday_source_parity_test.dart test/holiday_overrides_test.dart test/lunar_calendar_util_test.dart
```

4. 같은 터미널에서 웹을 빌드한다. 이 명령이 수정된 Dart 목록을 `build/web`의 웹 파일로 만든다. **빌드만으로 공개 사이트는 바뀌지 않는다.**

```powershell
flutter build web --release -t lib/web_main.dart
```

5. 빌드가 성공하면 같은 프로젝트 루트에서 아래 명령으로 **친구 공유 웹사이트**에 배포한다. Firebase CLI 로그인이 필요하다고 나오면 `firebase login`을 한 번 실행하고 배포 명령을 다시 실행한다. 루트 `firebase.json`의 Hosting 공개 폴더는 `build/web`이다. `admin_dashboard/` 사이트는 별도다.

```powershell
firebase deploy --only hosting --project shiftbell-29f31
```

6. `https://shiftbell-29f31.web.app`에서 친구 달력 링크를 열고 바뀐 날짜·이름과 앞뒤 날짜를 확인한다. 오래 열어 둔 탭은 새로고침하고, 필요하면 새 브라우저에서도 본다. 정적 파일 캐시 때문에 일부 방문자는 약 하루 동안 이전 웹 파일을 볼 수 있다.

### C. 앱 코드까지 다음 버전에 포함할 때

Firebase `add`에만 등록해도 **원격 조회가 가능한 앱**에는 앱 업데이트 없이 적용된다. 그러나 앱의 기본 날짜 목록에도 남기고 싶다면 `lib/utils/holiday_util.dart`와 `android/app/src/main/kotlin/com/hwani1103/shiftbell/CalendarWidgetHolidays.kt`의 날짜를 함께 수정한다. 앞의 테스트로 Dart와 Kotlin 기본 날짜가 일치하는지 확인하고, 위 버전 올리기 절에 따라 앱 버전을 올려 내부 테스트와 Play 배포를 한다. 기본 목록을 바꾼 뒤에도 원격 `add`·`remove`가 우선하므로 두 목록이 충돌하지 않는지 확인한다. 앱 코드를 배포하지 않는 2030년 원격 등록에는 이 단계가 필요 없다.

Firestore 보안 규칙은 기존 `app_config` 문서의 읽기(get)만 허용하고 앱의 쓰기는 금지한다. 콘솔에서 공휴일 문서를 수정하는 데 규칙 배포는 필요 없다.

## 3. 달력이 보여주는 연도 범위 넓히기

**결론부터**: 이건 급하게 안 해도 됩니다. 지금 코드가 "오늘 기준 앞뒤 3년"으로 자동으로 움직이게 되어 있어서, 시간이 지나면 알아서 더 먼 미래까지 보여줍니다. 다만 지금 당장(2026년 기준) 달력을 미리 2050년까지 넉넉하게 열어두고 싶다면, 아래처럼 숫자 하나만 바꾸면 됩니다.

### 지금 왜 2029~2030년 이후가 안 보이나요?

**위치**: `lib/screens/calendar_tab.dart` 파일에서 `TableCalendar(` 로 시작하는 부분 바로 아래, 이 두 줄입니다 (Ctrl+F로 `firstDay:` 검색하면 바로 찾아짐):

```dart
firstDay: DateTime(DateTime.now().year - 3, 1, 1),
lastDay: DateTime(DateTime.now().year + 3, 12, 31),
```

이 두 줄이 "달력을 앞뒤로 넘겼을 때 어디까지 갈 수 있는지"를 정합니다.
- `DateTime.now().year` = 앱을 실제로 켠 그 순간의 "올해" (예: 지금 켜면 2026)
- `- 3` / `+ 3` = 올해 기준으로 3년 전 / 3년 후까지

그래서 2026년에 켜면 2023년 1월 ~ 2029년 12월까지만 달력을 넘길 수 있어요. **중요한 건 이게 "2029년"이라고 고정된 숫자가 아니라 "지금으로부터 +3년"이라는 점** — 그러니까 2027년에 이 앱을 켜면 자동으로 2024~2030년으로 범위가 넘어가 있습니다. 코드를 안 건드려도 시간이 지나면 저절로 따라가요. (단, 이미 사용자 폰에 깔려있는 예전 버전 앱도 이 계산을 "그때그때" 다시 하기 때문에, 업데이트를 안 해도 범위 자체는 계속 따라갑니다 - 코드를 바꿔야만 하는 건 "지금 당장 더 먼 미래까지 미리 열어두고 싶을 때"뿐입니다.)

### 2050년까지 미리 넓혀두고 싶다면

`+ 3`을 원하는 숫자로 바꾸면 됩니다. 2026년 기준으로 2050년까지 보고 싶으면 2050-2026=24, 여유 있게 `+ 25` 정도로:

```dart
firstDay: DateTime(DateTime.now().year - 3, 1, 1),
lastDay: DateTime(DateTime.now().year + 25, 12, 31),   // ⭐ 3 → 25로 변경
```

`firstDay`의 `- 3`(과거 방향)은 굳이 안 늘려도 됩니다 - 지나간 날짜를 그렇게 멀리까지 볼 일은 거의 없어서요. 늘리고 싶으면 같은 방식으로 숫자만 바꾸면 됩니다.

### 주의할 점
- 이 숫자를 아무리 키워도 **실제로 알람이 미리 만들어지는 건 아닙니다.** 알람은 항상 "오늘부터 10일치"만 자동 생성돼요 (이건 다른 로직이라 별개). 이 3번 항목은 순전히 "달력 화면에서 손가락으로 넘겨서 미래/과거 날짜를 구경하고, 근무를 미리 지정해둘 수 있는 범위"를 넓히는 것뿐입니다.
- 빨간날(2번 항목)은 이거랑 별개로 계속 매년 데이터를 채워야 해요. 달력 범위만 2050년까지 열어놔도, `_lunarHolidays`에 2031년 데이터가 없으면 2031년 달력엔 설날/추석 표시가 안 됩니다.
- 고친 뒤엔 다른 코드 수정과 마찬가지로 `flutter build appbundle --release --flavor prod --dart-define=ADMOB_BANNER_ID=<실제 배너 광고 단위 ID>`로 다시 빌드하고 버전을 올려서(위 1번) 배포해야 사용자 폰에 반영됩니다.

1) 형식·크기 제한(OBS1/2)의 제안
- 소유자 일치, 공개 get, list 금지 계약은 유지한다. create/update의 request.resource.data에 허용 필드 목록/필수 필드/기본 타입을 검사한다.

- request.resource.data.keys().hasOnly/hasAll, 필드 is string/bool/int/list/map/timestamp, size()로 바깥 구조와 개수는 제한할 수 있다. 단 map/list의 모든 멤버 타입·날짜 키·값 길이를 반복 검증하는 일반 문법은 없다. 바깥 타입/개수 검사만으로 모든 손상 payload를 막았다고 선언하지 않는다.
- 현재 앱은 JSON UTF-8 800KiB 업로드 상한도 둔다. map 개수 제한을 문서 총바이트 제한과 동일시하지 않는다. 완전한 서버 검증이 요구되면 저장 스키마 변경이나 신뢰할 서버의 쓰기 검증이 별도 필요하다.
- 구버전 호환은 legacy 필드 누락을 허용하는 분기와 새 프로토콜 분기를 구분해야 한다. 엄격 hasOnly/updatedAt==request.time 같은 조건을 운영 실제 구버전 payload 확인 없이 즉시 배포하지 않는다.

2) 삭제 후 부활·낮은 세대 쓰기(OBS3/4)의 제안
- 현재 _submitStop은 문서를 delete한다. 삭제하면 서버가 기억하던 generation도 없어져, create 규칙만으로 과거 회차 재생성을 구분할 수 없다.
- 새 프로토콜은 개인정보를 제거한 최소 tombstone {generation:g, revoked:true, updatedAt:serverTimestamp}를 남기고 클라이언트 physical delete를 막는 방식이 후보이다. 수신기는 revoked=true를 이미 인식하지만, 송신기 stop/delete와 재시작 세대 복구는 함께 바꿔야 한다.
- 서버 전이 초안:
  없음 → active(g>=1): 허용. 기존 삭제 전 높은 세대는 기록이 없으므로 전환 전 과거까지 보호했다고 볼 수 없음.
  active(g) → active(g): 같은 공유 세션 편집 허용.
  active(g) → active(g+): 새 세션으로 증가 허용.
  active(g) → revoked(h>=g): 같은/높은 세대 중지 허용.
  revoked(g) → active(h>g): 새 공유 시작만 허용. 같은 세대와 낮은 세대는 거부.
  revoked(g) → revoked(h>=g): 중지 재시도 허용.
  모든 g→낮은 세대 쓰기 및 클라이언트 delete: 거부.
- 같은 generation의 A→B→오래된 A 덮어쓰기는 위 규칙만으로 해결되지 않는다. 같은 공유 세션의 오래된 내용까지 보호하려면 write revision/서버 수렴 전략을 별도로 정해야 한다.
- 재설치/설정 손실로 로컬 세대가 서버보다 작아지는 경우의 복구가 필요하다. 서버 트랜잭션 기반 세대 배정은 온라인 복구에는 유효하지만, 오프라인에서는 트랜잭션이 실패하므로 현재 offline pending 동작을 그대로 대체할 수 없다.
- 구버전의 delete를 계속 허용하면서 이 부활 방지를 완전히 보장하는 것은 같은 경로에서는 양립하지 않는다. 새 프로토콜 전용 경로/버전 표시와 단계 전환, 또는 구버전 쓰기 지원 종료 중 제품 선택이 필요하다.
- tombstone을 언제 지울지도 정책이다. 지운 뒤 세대 기록이 사라지면 늦은 옛 create가 다시 가능하다. 보존 기간·계정 삭제·공유 재개·개인정보 없는 필드 범위를 함께 결정해야 한다.
