## 단계3 설계 방향(아직 제품 미적용)

최소한의 명시적 슬롯 정보가 필요하다. 기존 history에는 fixed/custom 구분이 없으며 DST gap에서02:30 템플릿이03:30으로 저장된다. 모든 종료 이력의 같은 시각을 차단하는 방식은 채택하지 않는다.

권장 적용안:
- DB28 비파괴 nullable `fixed_slot_time TEXT`를 alarms와 alarm_history에 추가. 값은 원래 템플릿의 현지 날짜·시각(yyyy-MM-ddTHH:mm:00), epoch/기기ID가 아니다. 기존 데이터는 null로 보존. 신규/repair/Native/Dart 버전 동기화 및 v27→28 실패 롤백 검사 필요.
- 고정 알람 생성의 PendingFixedAlarm/DesiredAlarm에 nominal slot을 보존. Alarm 모델/Native insert/onboarding가 전달. 스누즈는 원래 필드를 유지한다. 기존 매칭 행은 ID/예약을 바꾸지 않고 알려진 슬롯 필드만 보강한다.
- Native 끄기/스누즈/충돌/timeout/다음 알람 인계는 기존 같은 DB 트랜잭션에서 슬롯 필드도 history로 옮긴다. Dart 울림 삭제도 동일. 종료 이력 쓰기 실패 뒤 fixed 삭제만 진행하는 현재 fail-open 경계는 원자성 검토 후 조정.
- 읽기: 실제 소비 terminal만(swiped/timeout/snoozed/snooze_skipped_existing_alarm/superseded_by_next_alarm). 설정 교체 superseded 및 울리기 전 취소는 소비로 보지 않는다(기존 skip override 정책 유지).
- 새 이력은 명시 슬롯+shift+day_offset 사용. 구 이력(null)은 creation.source=auto, 같은 alarm_id·원래 슬롯·shift·day_offset이 모두 맞는 경우만 기존 저장 슬롯으로 인정. 근거 없는 custom/손상/모호 이력은 정상 알람을 막는 데 사용하지 않는다. 단순 ID join 금지.
- Native/Dart 모두 우선순위로 시간당 승자를 고른 뒤 소비 여부를 적용해, 끝낸 슬롯을 낮은 우선순위의 같은 시각 알람으로 채우지 않음. 소리 종류 변경은 같은 슬롯을 되살리지 않음. 다른 날짜/시각/근무/offset은 정상 생성. 스누즈 현재 행·절대 재울림 시각 보존.
- 기존 영구 history 백업/복원 병합이 새 nullable 필드를 보존하도록 검사. 초기화는 원래 이력을 지우는 경계에서 다시 시작 허용. 이력 보존 중 템플릿을 바꿨다 돌려도 이미 실제 끝낸 같은 슬롯을 자동 재생하지 않는다.
- 과거 DST gap 이력에 원래 템플릿 시각이 없으면 완전히 역추론할 수 없다. 근거 없이01시간을 빼는 보정 금지. 기존 기록으로 입증 가능한 저장 슬롯만 보호한다는 한계를 기록한다. 신규 슬롯 정보는 이 모호성을 예방한다.
- 검증 fixture는 v27 기대 파일을 보존하고 v28을 별도로 만든다. 테스트 기대값을 제품 SQL 실행 결과로 무비판적으로 덮지 말고, 기존 기대+명시 nullable 필드 추가를 독립 변환하며 migration 원자성/전후 데이터/다운그레이드 거부를 확인한다.

다음 즉시 작업: Native 수정 전 재현 결과 확정 → 설계 최종 확정/구현 → 같은 검사 PASS → 확장 회귀. 검사 실패를 지우거나 기대값을 낮추어 통과시키지 않는다.
