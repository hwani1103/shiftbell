## A. 백업 파일 2슬롯화 (직접 백업 1개 + 자동 백업 1개)

### 요구사항
- Download/ShiftBell에는 **항상 이 설치본의 백업 파일이 최대 2개**: "직접 백업" 1개, "자동 백업" 1개.
- 각각 새로 만들면 **같은 종류의 이전 파일만** 교체. 자동 백업이 직접 백업을 지우는 일은 없음.

### 현재 구조와 문제
- 직접(설정 "데이터 백업" → `BackupWatcher.backupNow(force: true)`)과 자동(`backupNow()`)이 **같은 네이티브 함수** `writeBackupFile`을 탐 → 파일에 종류 구분이 없음.
- 정리 규칙은 "최신 + 직전 1개"(X-07) → 직접 백업도 자동 백업 2번이면 지워짐.
- 파일명이 분 단위(`yyMMdd_HHmm`)라 같은 분에 두 번 쓰면 MediaStore가 `(1)`을 붙임.

### 설계
| 항목 | 내용 |
|---|---|
| 파일명 | `ShiftBell_Backup[_dev]_manual_yyMMdd_HHmmss.json` / `ShiftBell_Backup[_dev]_auto_yyMMdd_HHmmss.json` (초까지 → `(1)` 제거). 접두어 `ShiftBell_Backup`는 유지(1.0.23 이하 탐지·안내 문구와 호환) |
| 채널 | `writeBackupFile(content, kind)` — kind = `manual` \| `auto` |
| 쓰기 순서 | ① 새 파일 `IS_PENDING=1`로 씀 → ② **다시 읽어 JSON 디코딩·근무표 존재 검증**(직전 정상본 보존(X-07)을 없애는 대신 넣는 안전장치) → ③ 공개 → ④ **같은 kind의 옛 파일만** 삭제 |
| 옛 파일 추적 | prefs `backup_prefs`에 kind별 URI(`last_uri_manual`, `last_uri_auto`) + 전체 스캔 시 kind 접두어로 구분 |
| 1.0.23 파일 이관 | 첫 새 형식 **자동** 백업 성공 뒤, 이 설치본이 소유한 옛 형식 파일(`…_Backup_yyMMdd_HHmm*.json`, kind 없음)을 삭제. 옛 직접 백업이 섞여 있을 수 있으나 새 자동 백업이 더 최신이라 데이터 손실 없음 |
| 자동 탐지(재시작·복구 안내) | 두 파일 중 **백업 내부 저장 시각이 더 최근이고 검증 통과한 것**. 복원 확인 화면에 "직접 백업 · 9/23 22:46" 식으로 종류 표시 |
| 설정 화면 | "데이터 백업" 아래에 두 슬롯의 마지막 저장 시각을 각각 표시("직접 백업: 9/20 14:02 · 자동 백업: 방금") |
| 문구 | 도움말·복원 안내의 "여러 개면 가장 최근 것" → "manual(직접) / auto(자동) 두 개가 있어요. 보통 더 최근 것을 고르세요" |

### 한계(사양)
- 앱을 **지우고 다시 깔면** 이전 설치본 파일은 여전히 앱이 볼 수 없음(안드로이드 규칙, 저장소 권한 안 받음). 그때는 최대 2 + 옛 파일들이 됨 — 버그 아님(CLAUDE.md 백업 절 2026-09-17 정정 참고).

## B. 커스텀 알람 프리셋 (달력 상단 5칸)

### 요구사항(정리)
1. 달력 탭 상단 "2026년 9월" 줄의 **오른쪽 빈 공간**에 알람 프리셋 **5칸**.
2. 각 칸 = 시각 + 알람 종류(소리/진동/무음 등 기존 `alarm_types`). 영역을 눌러 5칸을 편집.
3. 프리셋을 **날짜에 탭 또는 드래그**하면 그 날짜·그 시각에 1회용 알람 생성.
4. 생성 시 검증: ① 지금보다 이전 시각이면 **생성 안 함** ② 같은 날짜·같은 시각 알람이 이미 있으면 거부 ③ 그날 알람이 이미 **5개**면 거부.
5. 생성 후 안내: "오늘 07:00에 알람이 예약됐어요" / 1시간 이내면 "32분 후에 알람이 울려요".
6. 이력·갱신·재부팅 재예약·사전 알림(20분 전)·울림 화면·제어 알림 7777 등 **고정 알람과 동일하게 동작**.

### 이미 있는 기반(새로 만들 필요 없음)
- `alarms.type = 'custom'`이 스키마·백업·복원에 이미 있음(백업은 "미래 custom만" 포함 — `backup_service.dart:98`).
- 갱신 엔진은 `type='fixed'`만 지우고 다시 만듦 → **custom 행은 자동 갱신이 건드리지 않음**. 재부팅·업데이트 때는 `readOtherFutureAlarms()`가 custom도 `AlarmWakeScheduler`로 재등록(#26).
- 울림·이력(`alarm_history`)·생성 로그(`alarm_creation_log`)는 알람 ID 기준이라 type과 무관하게 기록됨.

### 설계
**데이터**
- 프리셋 5칸: SharedPreferences `custom_alarm_presets`(JSON 배열 5개: `{time: "07:00" | null, alarmTypeId}`).
  → Native가 읽을 필요 없음 + CLAUDE.md "설정값은 DB 아님" 규칙 → **DB 마이그레이션 불필요**. `kBackupPreferenceTypes`에 등록해 백업·복원 포함.
- 생성되는 알람: `alarms` 행 `type='custom'`, `date`=그 날짜+시각, `alarm_type_id`=프리셋 값, `shift_type`=NULL(화면·울림 라벨은 "커스텀 알람"), `day_offset`=0.
- 생성 로그: `alarm_creation_log.source = 'custom_preset'`.

**생성 경로(단일 함수 `CustomAlarmService.assign(date, preset)`)**
1. 트랜잭션 안에서 검증: 과거 시각(→ `past`), 같은 시각 존재(fixed/custom 모두, → `duplicate`), 그날 알람 수 ≥ 5(fixed+custom, → `dailyLimit`).
2. 통과하면 `alarms` insert + `alarm_creation_log` insert 커밋.
3. **커밋 뒤** 네이티브 등록(기존 `scheduleNativeAlarm` → `AlarmWakeScheduler` 단일 경로 규칙 준수). 등록 실패(정확한 알람 권한 없음 등, #13)면 행을 지우고 "알람을 예약하지 못했어요 — 정확한 알람 권한을 확인해 주세요" 안내.
4. 결과별 토스트(위 5번 문구). 스낵바에 **[되돌리기]** 버튼(5초) — 잘못 누른 날짜 즉시 취소.

**삭제·확인**
- 날짜 상세 시트의 "고정 알람" 목록 아래 **"커스텀 알람"** 목록 + 삭제 버튼. 삭제 = DB 삭제 후 OS 취소(기존 삭제 경로 재사용).
- 다음 알람 탭 목록에도 "커스텀" 표시로 포함(현재 목록 쿼리가 type 구분 없이 읽는지 구현 때 확인).
- 달력 칸에 커스텀 알람이 있는 날은 작은 🔔 점 표시(선택 — 결정 항목 3).

**UI(상단 5칸)**
- 칸 모양: 시각만 보이는 작은 칩(`07:00`) + 종류 아이콘(소리/진동/무음). 비어 있으면 `+`.
- **탭으로 할당(기본)**: 칩을 누르면 "할당 모드" — 칩 강조 + 하단 안내줄 "날짜를 누르면 07:00 알람이 추가돼요 · [완료]". 모드 중 날짜 탭 = 생성. 칩을 다시 누르거나 [완료]를 누르면 종료. 할당 모드 중에는 기존 날짜 탭 동작(상세 시트)·길게 눌러 다중 선택을 잠시 끔.
- **드래그로 할당(보조)**: 칩을 길게 눌러 끌어다 날짜 칸에 놓으면 생성. 드래그 중 월 스와이프는 막음.
- **편집**: 칩 영역 오른쪽 끝 ✎ 버튼(또는 빈 칸 탭) → 하단 시트에서 5칸 각각 시각 선택·종류 선택·비우기.
- 좁은 화면(360dp 이하·큰 글씨)에서는 5칸이 한 줄에 안 들어갈 수 있음 → 칩 폭을 남은 폭 ÷ 5로 계산하고 글자 자동 축소(수면 위젯 칩과 같은 방식), 그래도 모자라면 가로 스크롤.
- 테마 10종 모두 헤더 구조가 다름(`_themeHeaderBackground` 등) → 헤더 공용 위젯 하나로 만들어 각 테마 헤더에 끼움.

**다듬은 점(요청에서 보완)**
- 자정 넘김: 프리셋 `00:30`을 9/23에 놓으면 **9/23 00:30**(그 날짜 기준). 이미 지났으면 거부.
- "하루 5개" 기준은 **그 날짜에 실제로 울리는 알람 수(고정+커스텀)**. 고정 알람은 전날/다음날 오프셋 때문에 이론상 5개를 넘을 수 있는데, 그 경우 그날은 커스텀 추가만 막힘(고정 알람은 건드리지 않음).
- 같은 시각 기준은 분 단위 일치.
- 근무를 바꿔도 커스텀 알람은 유지(근무와 무관한 1회 알람). 백업 복원 시 미래 커스텀은 이월(기존 규칙).
- 통계: `custom_alarm_assigned` 이벤트(파라미터: 결과 종류만, 시각 X) — `AnalyticsEvent.all` + 대시보드 `labels.js`/`mock.js` 동시 수정(CLAUDE.md 규칙).

### 영향 파일

## C. 문제 진단 로그 (사용자가 파일로 보내 주는 구조)

### 요구사항
- "알람이 안 울렸다", "백업이 안 됐다" 같은 신고 시 사용자가 **로그 파일 하나를 보내면** 원인을 가를 수 있게.
- 최소한 **① 권한 문제 ② 제조사 백그라운드 제한 ③ 앱 코드 결함** 중 무엇인지 구분.
- 개발자용 **해석 매뉴얼** 동봉.

### 설계
**① 기록(항상, 기기 안에만)**
- 앱 내부 저장소(Device Protected — 잠금 해제 전 알람 경로에서도 기록 가능)에 텍스트 로그 2개를 번갈아 씀(`diag_0.log`, `diag_1.log`, 각 최대 256KB → 총 512KB 상한, 오래된 것부터 덮어씀). 외부로 절대 자동 전송 안 함.
- Kotlin `DiagLog.kt` 하나(`DiagLog.e(event, key=value…)`), Dart는 채널 메서드 `diagLog`로 같은 파일에 기록. 한 줄 형식:
  `2026-09-23T06:59:58.120+09:00 | ALARM_FIRED | id=1234 planned=07:00:00 delayMs=-1880 screen=off`
- 기록 대상(이벤트 이름 고정 — 매뉴얼과 1:1)

| 분류 | 이벤트 |
|---|---|
| 알람 예약 | `SCHEDULE_OK`(id, 시각, 경로) · `SCHEDULE_FAIL`(id, 사유: 권한/예외) · `CANCEL` |
| 알람 울림 | `ALARM_FIRED`(예정 대비 지연 ms, 화면 상태) · `ALARM_STALE_IGNORED`(DB 시각 불일치) · `DISMISS`/`SNOOZE`/`TIMEOUT` |
| 갱신 | `REFRESH_START`(트리거: 앱실행/자정/부팅/알람수신…) · `REFRESH_DONE`(생성/삭제/재등록 수) · `REFRESH_FAIL` |
| 시스템 | `BOOT`(잠금 전/후) · `PKG_REPLACED` · `EXACT_ALARM_PERM_CHANGED` · `TIME_CHANGED` |
| 백업 | `BACKUP_WRITE_OK/FAIL`(kind, 크기, 실패 사유) · `BACKUP_SKIP`(사유: 내용 동일/복원 중) · `RESTORE_STEP`(단계, 결과) |
| 친구 공유 | `SHARE_SYNC_OK/FAIL`(오류 코드만) |

- **기록 금지**: 메모·일정 내용, 근무명, 친구 이름, 공유 코드. 알람은 ID·시각·종류만(개인정보처리방침에 "사용자가 직접 보낼 때만 전달되는 진단 기록" 한 줄 추가).

**② 내보내기(사용자가 직접)**
- 설정 → 도움말 근처 **"문제 신고용 진단 파일 만들기"** → `Download/ShiftBell/ShiftBell_Diag_yyMMdd_HHmmss.txt` 저장(이 종류는 항상 1개만 유지) + 바로 **공유 시트**(카카오톡·메일 등)로 보내기 버튼.
- 파일 맨 앞에 **내보내는 순간의 상태 스냅샷**을 붙임 — 이게 원인 구분의 핵심:
  - 앱 버전/빌드, 제조사·모델, Android 버전, 설치 경로(스토어/직접)
  - 권한: 알림 · 정확한 알람 · 다른 앱 위에 표시 · 전체 화면 알림(Android 14+) · **배터리 최적화 제외 여부** · **백그라운드 제한 여부**(`ActivityManager.isBackgroundRestricted`) · **앱 대기 버킷**(`UsageStatsManager.appStandbyBucket` — RARE/RESTRICTED면 제조사/OS 제한 신호)
  - **최근 프로세스 종료 사유**(`getHistoricalProcessExitReasons`, Android 11+) — 강제 종료·저메모리·제조사 킬 구분
  - 다음 알람 10개: DB 시각 vs **OS에 실제 등록돼 있는지**(PendingIntent 존재 확인)
  - 마지막 갱신 시각·결과, 마지막 백업 시각(kind별), 복원 잠금 상태
- 이어서 로그 2개를 시간순으로 합쳐 붙임.

**③ 해석 매뉴얼** — `docs/진단로그_해석_매뉴얼.md`
- "증상 → 먼저 볼 줄 → 판정" 표. 예:
  - 알람 안 울림 + 스냅샷 `exactAlarm=DENIED` 또는 `SCHEDULE_FAIL reason=permission` → **권한**
  - `SCHEDULE_OK` 있음 + `ALARM_FIRED` 없음 + 종료 사유 `USER_REQUESTED`/`FREEZER`/버킷 `RESTRICTED`/`isBackgroundRestricted=true` → **제조사·OS 백그라운드 제한**
  - `ALARM_FIRED delayMs`가 수 분 이상 + 배터리 최적화 미제외 → **제조사 절전**
  - 갱신 뒤 `SCHEDULE_OK` 자체가 없음 / DB엔 있는데 OS 미등록 / `REFRESH_FAIL` → **앱 코드 결함**(이벤트 이름 → 해당 소스 파일·함수 표 포함)
  - 백업 안 됨: `BACKUP_SKIP reason=same_content`(정상) / `BACKUP_WRITE_FAIL reason=insert_null`(저장공간·OEM) / 기록 자체 없음(트리거 미호출 = 코드)
- 이벤트 이름마다 "어느 파일 몇 번째 함수에서 찍히는지" 표 → 코드까지 따라갈 수 있게.

### 크기·성능
- 라이브러리 없음, 파일 쓰기는 한 줄 append + 크기 확인만 → 알람 경로 지연 무시 가능 수준. 쓰기 실패는 삼킴(로그 때문에 알람이 실패하면 안 됨).

## D. 공휴일 원격 갱신 (Firebase)

### 요구사항
- 대체공휴일·임시공휴일이 생기면 **앱 업데이트 없이** Firebase에서 추가/삭제 → 사용자가 앱을 켜거나 돌아올 때 반영. 연도 제한 없음.
- 무료(Spark) 한도 안에서.

### 현재
- `holiday_util.dart`(이름 포함, 2025~2029 하드코딩) ↔ `CalendarWidgetHolidays.kt`(날짜만, 복제본) — 손으로 맞추는 이중 구현(CLAUDE.md ⚠️1).
- 업데이트 안내가 이미 `app_config/android` 문서 1개를 읽음(`update_service.dart`, **기기당 6시간에 최대 1번**).

### 설계
**Firestore**
- `app_config/android`에 필드 1개 추가: `holidaysVersion`(숫자).
- 새 문서 `app_config/holidays_kr`:
  ```
  version: 3
  updatedAt: 2026-09-23
  add:    { "2027-06-03": "지방선거", "2028-05-08": "임시공휴일", ... }   // 추가·이름 변경
  remove: [ "2026-06-03" ]                                             // 하드코딩 목록에서 빼야 할 날
  ```
- 보안 규칙: 기존 `match /app_config/{document}`가 이미 get만 허용·write 거부 → **규칙 변경 불필요**.

**앱**
- 업데이트 체크 때 받은 `app_config/android`의 `holidaysVersion`이 로컬 캐시 버전보다 크면 그때만 `holidays_kr` 1회 읽기 → SharedPreferences에 캐시(`holiday_overrides_json`, `holiday_overrides_version`).
- 최종 공휴일 = 하드코딩 목록 − `remove` + `add`. 형식이 잘못된 항목은 무시(앱이 절대 죽지 않게).
- 달력·친구 달력·웹 뷰어·위젯 모두 같은 결과 사용:
  - Dart: `getHolidayName()`이 캐시 병합 결과를 보게 변경.
  - 위젯(Kotlin): Dart가 병합된 **날짜 목록**을 네이티브 prefs에 써 주고 위젯 갱신 → `CalendarWidgetHolidays.kt`는 prefs 우선, 없으면 기존 하드코딩(첫 실행·오프라인 대비).
  - 웹 뷰어(`web_main.dart`)도 같은 문서를 읽도록(웹은 캐시 없이 로드 시 1회).
- 반영 시점: 앱 실행·포그라운드 복귀 시(6시간 쿨다운 공유). **즉시 반영이 필요할 때**는 `holidaysVersion`만 올려도 쿨다운 때문에 최대 6시간 지연될 수 있음 → 결정 항목 5.

**운영 방법(개발자)**
- Firebase 콘솔 → Firestore → `app_config/holidays_kr`의 `add`/`remove` 수정 → `version` +1 → `app_config/android`의 `holidaysVersion`을 같은 값으로.
- 실수 방지용 로컬 스크립트 `admin_dashboard/sync/holidays.mjs`(JSON 파일 → 형식 검증 → 업로드, 서비스 계정 필요)도 선택 제공.
- `업데이트_가이드.md`의 "공휴일 추가" 절을 이 절차로 교체. 하드코딩 목록은 **안전망**으로 계속 유지(2030년 이후 항목은 원격으로만 추가해도 됨).

### 무료 티어 검토 (Firestore Spark: 읽기 5만/일, 쓰기 2만/일, 저장 1GiB, 전송 10GiB/월)
- 공휴일 때문에 **새로 늘어나는 읽기 = 버전이 바뀐 날, 앱을 연 기기당 1회**. 평소엔 0(기존 `app_config/android` 읽기에 필드만 얹음).
- 기존 업데이트 체크 읽기: 기기당 하루 최대 4회(6시간 쿨다운). DAU 1만 명이 하루 4번 넘게 앱을 여는 극단값에서도 4만/일로 한도 안. **DAU가 1만을 넘으면 쿨다운을 12시간으로** 올리는 게 안전(대시보드 DAU로 판단).
- 문서 크기: 연 20~30개 항목 × 수십 년이어도 수 KB → 1MiB 문서 한도와 무관.
- 결론: **무료 티어로 충분**.

## E. 웹 뷰어 캐시 개선 (Firebase Hosting 전송량)

- 현재 `firebase.json` 호스팅 헤더가 모든 파일 `no-cache, no-store, must-revalidate` → 재방문해도 `main.dart.js`(압축 약 590KB)·에셋을 매번 다시 받음. Spark 호스팅 전송 한도 **360MB/일** → 하루 약 400~600회 열람에서 막힐 수 있음.
- 변경: 헤더를 `no-cache`(**저장은 하되 매번 서버에 최신 여부 확인**, ETag → 변경 없으면 304)로. 재방문 전송량이 수백 바이트로 줄고, 새 배포는 즉시 반영됨.
- **근무표 데이터는 캐시 대상 아님** — Firestore에서 매번 읽음(기존 동작 그대로).
- 앱 업데이트 불필요, `firebase deploy --only hosting`(웹 뷰어 사이트)만. 배포 후 `curl -I`로 헤더·304 확인.
