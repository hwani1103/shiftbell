3. F01 — DB 초기화 완료 뒤 네이티브 실패 시 화면이 이전 상태를 유지
분류: P2 / 코드 확인 + 호스트 실패 주입 재현 / 제품 수정 미실시.

근거

MainActivity는 이 Outcome을 Flutter 오류로 전달하지 않는다. 따라서 통상적인 DB/OS 취소 실패가 곧바로 F01의 예외 경로를 만든다는 설명은 부정확하다. F01 재현은 이 방어 밖의 예외가 MethodChannel을 통해 Flutter까지 전달됐을 때의 조건부 결과다.

재현한 사실
① 임시 DB에 근무표와 일반 알람1개를 넣고 ScheduleNotifier에 로드한다.
② stopRingingAlarm만 PlatformException을 반환하도록 한다.
③ resetSchedule이 예외를 반환하고 DB의 shift_schedule/alarms는0행, notifier.state에는 이전 근무표가 남는 것을 확인한다.
④ cancelNativeAlarm만 실패하는 경우도 동일하게 확인한다.
⑤ 두 경우 모두 뒤쪽 cancelAlarmGuard 호출은 수행되지 않았다.

영향과 한계
- 사용자는 초기화가 안 된 것처럼 보거나 오류만 볼 수 있지만 실제 데이터는 이미 초기화된 상태다. 재시작/재조회 후에는 비어 있는 DB가 반영된다.
- 사용자가 의도하지 않은 일반 사용 데이터 삭제를 재현한 것은 아니다. 명시적으로 초기화를 실행한 뒤의 상태/안내 불일치다.
- 삭제된 예약이 반드시 다시 울린다고 단정하지 않는다. 수신 시 DB 재검증은 별도의 방어선이고, 이미 울리는 알람과 OS 취소 실패는 별도로 다뤄야 한다.
- 모든 알람 삭제는 동일 구조를 정적으로 확인했다. 별도 UI/실기기 실패 주입은 하지 않았다.
- prod는 Native 취소 후 DB 삭제 순서였고 dev는 DB 먼저 확정하는 구조로 변경됐다. Native cancelIfGone과의 정합성을 위해 DB 우선은 필요하며, 예전 순서로 단순 되돌리는 해결은 부적절하다.

권장 해결안(미구현)
- DB commit을 기준으로 provider/화면 상태를 확정하고, Native 정리 결과를 별도로 수집한다.
- 한 ID의 실패로 나머지 ID의 취소/정리까지 중단하지 않는다. 실패 ID 재조정 또는 재시도 경로를 둔다.
- 호출자에 DB 완료 여부와 OS 정리 미완료 여부를 구분해 반환한다. 초기화 화면에는 DB 실패와 부분 완료를 구분해 안내한다.
- 실패를 무조건 삼켜 완전 성공으로 표시하거나 DB 삭제를 되돌린 것처럼 안내하지 않는다.
- 수정한다면 정상 초기화·공유 저장 실패·Native stop/cancel 실패·이미 울리는 ID·남은 ID 정리를 검사한다. P0 정리 경로를 건드리는 범위에 맞춰 필수 회귀 실행 여부와 대표 실기기 범위를 정한다.

4. C01 — 수면 날짜 그룹핑의 DST 경계 잔여
분류: 조건부 P2 / 정적 확인 + 시간대 산술 예시 / Android 앱 재현 미실시.

근거
- lib/services/condition/sleep_day_slots.dart:173 전날을 startDay.subtract(Duration(days:1))로 계산.
- 같은 파일:286 날짜 목록을 d.add(Duration(days:1))로 이동하고 :287 byDay[d]로 날짜 키를 조회.
- 주변 shift_pattern_analyzer/work_hours/calendar_dates는 달력 날짜 필드 이동으로 바뀌었지만 이 그룹핑 경로에는 24시간 이동이 남아 있다.
- prod에서도 해당 Duration 계산은 존재했다. dev에서는 근무시간 정보가 없어도 00~05시 취침을 전날로 묶는 규칙이 추가되어 영향 가능한 입력이 넓어졌다.

산술 예시
- Europe/Berlin 2026-03-30 00:00(+02)에서24시간을 빼면 03-28 23:00(+01)이다. 원하는 달력 전날03-29 00:00과 다르다.
- 03-29 00:00(+01)에24시간을 더하면 03-30 01:00(+02)이다. midnight 키와 일치하지 않는다.
- 이런 값이 그룹핑/조회 키가 되면 해당 날짜 수면이 비거나 날짜 귀속이 어긋날 수 있다. 저장된 원본 수면행 삭제를 의미하지 않는다.

대상과 검증 경계
- 현재 외국어 앱은 수면 기능을 제공하지 않는다. 한국어 앱을 DST가 있는 해외 시간대에서 사용하는 경우가 직접 대상이다. 한국 표준시의 일상 사용에 DST 영향은 없다.
- timezone 패키지로 위 산술을 확인했다. 현재 Windows 로컬 DateTime 환경에 DST를 구성하지 않았고 실기기 시간대도 바꾸지 않았다. 이것을 앱 실측 PASS/FAIL로 기록하지 않는다.
- 기존 한국 시간대 수면 귀속 검사 PASS가 DST 날짜 키까지 검증했다는 뜻은 아니다. 기존 M03/DST 검증 경계와 연결한다.

권장 해결안(미구현)
- 날짜 이동은 DateTime(year,month,day±N) 또는 공통 calendarDate 함수를 사용하고 날짜 키를 일관되게 정규화한다.
- DST 시작/종료를 끼는 수면 슬롯·귀속·통계 경로를 함께 확인한다. 실제 수면 지속시간/스누즈처럼 경과시간이 목적일 때는 Duration을 유지한다.
- 증거: artifacts/final_code_review_2026_10_11/dst_calendar_arithmetic_probe.dart 및 dst_calendar_arithmetic.log.

10. 실제 사용 노출과 출시 전 수정 필요성 — 후속 평가

F01:2/10. 초기화/전체 삭제를 명시 실행하고, 삭제할 알람이 있으며, DB commit은 성공한 다음 Native 내부 방어 밖의 예외가 Flutter로 전달되어야 한다. 정상 DB open/조회/OS 취소 오류는 상당 부분 Native에서 처리되므로 실패 주입2건을 자연 발생 빈도로 해석하지 않는다. 실제 자연 발생 제보/재현은 없다. 발생하면 주로 삭제된 DB와 이전 화면의 불일치/안내 문제가 남고 재시작·재조회·재실행으로 수렴할 수 있다. 사용자 의도 밖의 임의 데이터 삭제나 평상시 알람 누락을 재현한 것이 아니다. 방어 보완 가치는 있으나 이번 출시 차단 사유로 보지 않는다.
