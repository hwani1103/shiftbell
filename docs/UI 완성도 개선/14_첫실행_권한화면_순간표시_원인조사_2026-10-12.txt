첫 실행 권한 화면 직전 순간 표시 — 코드 조사 결과
사용자 관찰: 설치 후 첫 실행에서 약 0.1초 앱 UI/올리브 버튼처럼 보이는 화면이 나타난 뒤 권한 화면이 나옴.
마지막 지시: 코드만 분석하고 결과 및 실기기 필요 여부를 보고한 뒤 PC 종료.

확인한 사실
1. main.dart InitialRouter는 permissions_requested가 false이면 PermissionIntroScreen으로 바로 이동한다. 앞서 OnboardingScreen을 그리는 정상 경로는 없다. 화면 전환 시간은 zero.
2. StartupGate의 정상 초기 상태 및 InitialRouter는 흰 빈 화면이다. native launch_background도 흰색이다. 옛 SplashScreen은 정상 진입 경로에서 사용되지 않는다.
3. PermissionController의 최초 값은 빈 PermissionSnapshot이다. PermissionPanel.initState에서 비동기 refresh를 실행한다. 초기 unknown 상태에서는 권한 카드들이 표시되고, 실제 조회 후 granted/notApplicable 카드는 사라진다. 이 때문에 같은 권한 화면 안에서 첫 프레임과 조회 완료 프레임의 카드/버튼 배치가 달라질 수 있다.
4. 호스트 테스트에서 조회를 지연시켜 이 변화가 재현됨: 처음 표시되던 정확한 알람/전체화면 항목이 실제 상태 적용 후 숨겨짐. 전후 모두 권한 화면이며 근무명 온보딩 화면은 나타나지 않음. test/onboarding_typography_roles_test.dart, 6차 123 PASS 로그에 포함.
5. 이 초기 snapshot/갱신/필터/라우팅 경로에는 debug 전용 분기가 없다. 따라서 확인한 재배치 현상은 debug에만 한정된 코드가 아니다. 사용자가 본 순간 화면의 정확한 원인이 이것이라고 확정할 수는 없다.

플랫폼상 가능한 별도 요인 (이번 현상의 원인으로 확인되지 않음)
- Android는 활동 재진입 시 이전 task snapshot을 시작 화면으로 표시할 수 있음. 디버그 전용 기능이 아님.
  https://source.android.com/docs/core/perf/task-snapshots
- Flutter debug JIT의 타이밍/지연은 profile/release와 다를 수 있음.
  https://docs.flutter.dev/perf/ui-performance
- 읽었던 OS snapshot 로그는 운영 패키지 com.hwani1103.shiftbell에 관한 것이므로 dev 첫 실행 현상의 증거로 사용하지 않음.

판정 및 한계
- 정상 코드상 ‘근무명 온보딩 → 권한 화면’ 전환은 발견되지 않음.
- 확인된 유력 후보: 권한 실제 상태를 기다리지 않고 첫 UI를 표시하여 발생하는 순간 재배치.
- ‘debug에서만 발생’ 여부와 사용자 관찰 화면의 동일성은 코드만으로 확정 불가.
- 실기기 확인 필요: 설치 상태를 구분한 첫 실행 화면 녹화와 dev 로그 시각 대조, debug 및 profile/AOT 동일 조건 비교. profile에서 재현되면 debug 전용 가설을 배제할 수 있지만 release 자체 확인 없이 release 무발생을 보장할 수 없음. release 빌드는 사용자 명시 승인 시에만 수행.
- 앱 데이터 삭제/재설치, startup/권한 동작 수정, release 빌드는 수행하지 않음. USB 단절 후 사용자 지시에 따라 코드 조사로 마무리.

후속 제안
실기기에서 권한 카드 재배치가 원인으로 확인되면, 최초 snapshot 조회까지 안정된 로딩 상태를 유지하거나 첫 화면 상태를 미리 준비하는 방식으로 개선한다. 이 변경은 권한 진입/복귀 P0 영향 검토와 check_critical_release.ps1 -Build 대상이며 별도 작업으로 진행한다.
