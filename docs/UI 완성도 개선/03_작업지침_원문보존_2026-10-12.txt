교대시계 UI 일관성·완성도 개선 — 작업 목록
작성일: 2026-10-12

■ 다음 세션 시작 지침
이 문서를 먼저 읽고 프로젝트 AGENTS.md와 기존 미커밋 작업을 확인한 뒤 시작한다.
첫 작업은 실제 코드·진입 경로에 근거한 전체 화면/팝업 전수 목록 작성이다.
아직 전체 화면 원장이나 모든 공통 요소의 최종 디자인이 완성된 상태는 아니다.
목록화 단계에서는 제품 코드를 수정하지 않고, 목록과 빠진 범위·외부 제약부터 보고한다.

현재 합의:
- 세이지는 형태·여백·카드의 기본 방향이며, 시안의 모든 요소를 일괄 채택하지 않음
- 고정 알람 생성/수정의 기존 AlarmTimePicker 조작 방식을 유지 기준으로 삼음
- 공통 구조 하나 + 블루/세이지/오트밀 색상 3종 방향
- 색상은 역할별 토큰으로 중앙 관리하고 Flutter ThemeData/ColorScheme 및 추가 색상 묶음으로 적용
  주요/보조/삭제/오류/선택/비활성·배경/카드/팝업·글자/테두리를 구분
  사용자 선택은 저장하고 화면에 반영. 달력 테마·근무별 의미 색상과 구분
- 전체 목록·규칙·공통 요소를 준비한 뒤 온보딩부터 사용자 흐름 순서로 적용
- 앱 소유 화면은 조건부·중첩·오류·백업·일정관리까지 포함해 빠짐없이 관리
  SDK/시스템 화면도 흐름 목록에 포함하되 수정 가능한 범위와 외부 제약을 명시
- 현재 출시본을 보존하고 dev에서 진행. 기능 의미·데이터·알람 예약 정책 유지
- 배경 변화·다음 알람 요약·애니메이션은 공통 UI 안정화 이후 별도 단계

첫 결과물: 화면 ID·사용처·구현 주체·현재 방식·상태별 진입·유지/변경 후보가 연결된 전수 원장.
이후 요소별 시안을 확정하고 공통 컴포넌트 제작, 화면별 적용·검증으로 진행한다.

■ 목적·진행 원칙
기존 기능과 데이터 동작을 유지하면서 앱 전체의 디자인·사용성을 개선한다.
현재 준비된 출시본을 먼저 업데이트하고, 출시 기준을 보존한 뒤 dev에서 진행한다.
약 한 달 후 후속 업데이트를 목표로 하되, 완성도와 검증 결과에 따라 범위를 조정한다.
아래 목록은 개선 후보이며, 작성 자체가 모든 항목의 구현 착수를 뜻하지는 않는다.

■ 1. 사용자 제안
- 시간대별 배경색: 새벽·아침·낮·저녁·미드나이트 5단계
- 국가보다 기기의 현지 시간대 기준으로 배경 적용
- 시간대별 배경색 부드러운 전환
- 자동 배경 ON/OFF & 고정 배경색 선택
- 배경색에 따른 텍스트·아이콘·카드 대비 조절
- 달력 테마와 시간대별 배경 조합 검증
- 메인 달력 상단: 좌측 년월 유지, 우측 다음 알람 요약
- 다음 알람은 100% 표시용: 터치·수정·이동 없음
- 다음 알람 날짜·근무명·시간·소리/진동 표시
  예: 다음 알람: 오늘 · 주간근무 · 07:30 · 진동
- 스누즈 알람 구분 & 다음 알람 없음 표시
- 작은 화면에서는 년월·달력 조작 영역을 침범하지 않는 배치
- UI 일관화 후 절제된 애니메이션 적용

  고정 크기 유지 의견을 보존하며, 시스템 확대 지원 여부는 이번 작업의 확정 요구사항으로 보지 않음
  최종 결정 시 가독성·접근성과 화면 밀도를 함께 비교하고, 확정된 정책 안에서 잘림을 검증

■ 5. 권장 진행 순서 — 전수 목록 후 온보딩부터 적용
1) 현재 출시본·커밋·AAB 기준 보존, prod/dev 작업 구분
2) 전체 화면·팝업·시트·선택기·native UI·외부 SDK 화면을 전수 목록화
   소스 호출 경로와 실제 진입 경로를 함께 확인하고, 조건부/오류/복구 화면도 포함
3) 유지할 요소와 바꿀 요소 확정, 화면 유형·크기·닫기·Back·전환 규칙 결정
   세이지는 형태/여백의 방향으로 채택하며 모든 세이지 시안 요소를 그대로 채택하지 않음
   고정 알람 생성/수정에서 사용하는 기존 시간 picker의 조작 방식은 유지 기준으로 사용
4) 공통 버튼·카드·칩·입력·팝업·선택기와 색상 토큰 기반 제작
   실제 대표 창 몇 개로 조합을 확인한 뒤 공통 요소를 확정하되, 해당 화면을 먼저 완성할 필요는 없음
5) 사용자 선호 순서로 적용: 시작/온보딩 → 권한/광고 동의 진입 → 메인 탭 → 하위 화면/팝업
   설정·백업/복원·일정관리·수면/회복·메모·공유 등 전수 목록의 모든 앱 소유 화면을 순차 적용
6) 목록 ID마다 구현·디자인 확인·기능 영향 검사·실기기 확인 상태 기록
   화면별로 닫기·Back·입력·키보드·SafeArea·전환 검사를 완료하고 다음 화면으로 진행
7) 전체 목록과 소스 호출 지점을 다시 대조해 미적용/미검증/외부 제약 항목 확인
8) 달력 테마·시간대별 배경·다음 알람 요약·애니메이션은 공통 UI 안정화 후 별도 단계로 진행
9) 최종 후보 기능 전수 검사 & 레이아웃 실기기 검증
10) 실제 prod 업데이트 설치·데이터 보존·핵심 알람 확인
※ 온보딩부터 진행하는 순서도 타당함. 누락 방지는 특정 화면 순서가 아니라 전수 목록·공통 요소·완료 증거로 확보한다.

■ 6. 검증 원칙
- 화면별 변경 직후 터치·스크롤·잘림·키보드·뒤로가기 확인
- 시스템 Back 버튼·뒤로가기 제스처·화면 내 뒤로가기/닫기·바깥 탭·시트 스와이프의 결과 대조
- 페이지/팝업 크기·전환 방향·중첩 해제 순서·미저장 변경 보존 여부 검증
- 시간별 배경·다음 알람 요약·애니메이션은 새 표시 기능으로 별도 검증
- 배경 시간 판정은 기존 알람 시간대·예약 계산과 분리
- 다음 알람 표시는 기존 실제 예약 상태를 활용하고 별도 예약 로직을 만들지 않음
- 기능 전수 검사를 마지막에 하되, 변경 영향 검사는 작업 중에도 수행
- Android 기능 검증은 dev debug 기본, release 빌드는 사용자 명시 요청 시에만 실행
- 알람·권한 등 P0 또는 출시 언어 기능/리소스 구조 변경 시 필수 회귀 검사 실행
  tools/check_critical_release.ps1 (빌드가 필요한 변경은 -Build)
- 실기기 잠금 알람·제조사 검증은 기존 권한 P0 회귀 기준 적용
- 공통 번역·한국어 전용 기능 경계 및 공개 웹 뷰어 의존성 보존
- 기존 PASS는 변경 영향이 있는 범위만 재검사
- 최종 검사 이후 수정이 생기면 영향 범위 재검증

■ 7. 화면 유형·팝업 크기·뒤로가기·전환 규칙
- 먼저 모든 화면의 현재 표시 방식·크기·버튼 위치·닫기 동작·등장 방향을 목록화
- 팝업/모달은 별개 크기 등급이 아님: 모달은 뒤 화면 조작을 막는 동작 방식
  대화상자·바텀시트·전체화면 편집 중 무엇을 사용할지는 작업의 길이와 역할로 결정
- 짧은 확인·삭제·안내: 작은 중앙 대화상자
- 간단한 값 선택·짧은 보조 작업: 공통 선택창 또는 바텀시트 중 기본 형식을 정함
  같은 역할의 시간·기간·년월 선택기는 같은 형식·조작 규칙을 사용
- 긴 입력·여러 항목 편집: 전용 페이지 또는 전체화면 편집으로 분류
- 일반 상세 조회·설정 하위 메뉴: 일반 페이지
- 크기는 소형/선택형/전체화면의 공통 기준으로 관리하고 임의 중간 크기를 늘리지 않음
  내용·기기 폭에 따라 높이/최대폭·스크롤을 조정하며, 모든 팝업을 동일 크기로 강제하지 않음
- 화면별 선택 근거와 예외를 기록: 작은 팝업→큰 팝업→페이지가 무작위로 섞이지 않게 함
- 일반 페이지: 좌측 상단 뒤로가기 화살표, 부모 화면으로 한 단계 복귀
- 독립 편집·모달: 공통 위치의 X 또는 취소로 해당 작업 닫기. 일반 페이지 복귀와 의미 구분
- 같은 종류의 모달에서는 X 위치를 고정하고, 같은 역할의 버튼 위치·아이콘·문구를 고정
  어떤 창은 우하단 뒤로가기, 다른 창은 좌상단 X로 닫는 임의 혼용 제거
- 확인·저장·삭제는 결과가 드러나는 문구 사용. 취소/닫기와 저장/완료를 분리
- 하단 동작 버튼 순서 통일: 한국어 등 LTR 화면은 취소 왼쪽, 주요 실행 오른쪽을 기본안으로 검토
- 시스템 Back 버튼·뒤로가기 제스처와 화면 내 닫기/복귀는 같은 종료 규칙을 공유
  단, 키보드가 열린 상태의 첫 Back은 키보드 해제일 수 있으므로 화면 닫기와 단계 구분
- 중첩 선택창은 가장 위의 창만 닫고, 부모 입력값·스크롤·선택 상태를 보존
- 미저장 입력이 있을 때 이탈 확인/폐기 정책을 일관되게 적용하고 Back을 저장으로 취급하지 않음
- 바깥 탭·아래로 스와이프 종료 허용 여부를 역할별로 정하고, 편집값이 조용히 사라지지 않게 함
- 전환 방향은 역할별 통일: 일반 페이지는 전진/복귀 방향 전환, 중앙 창은 짧은 페이드/스케일,
  바텀시트는 아래에서 등장하고 아래로 닫힘. 같은 역할에 좌우/상하 전환을 임의 혼용하지 않음
- 표시와 종료는 짝을 이루는 모션 사용, 속도·강도와 시스템 모션 축소 대응 통일
- 알람 해제·스누즈·권한 설정 복귀·복원 중단 등 기능 동작이 연결된 닫기는 예외를 먼저 확인
  화면 규칙 통일을 이유로 기존 기능 의미를 바꾸거나 모든 닫기를 단일 동작으로 치환하지 않음

■ 8. 앱 전체 테마 3종 선택 — 검토 의견
- 달력 테마와 별개로 쿨 블루/소프트 세이지/웜 오트밀의 앱 전체 색상 세트를 제공하는 것은 검토 가능
- 권장 구조: 하나의 공통 화면·컴포넌트·내비게이션 체계 + 선택 가능한 색상 토큰 3종
- 저장/확인·삭제·오류·선택·비활성 색상 의미는 모든 테마에서 동일하게 유지
- 팝업 종류·크기·X/뒤로가기 위치·화면 전환 방향·선택기 방식은 테마별로 바꾸지 않음
- 기존 시안은 구조 차이도 탐색하기 위한 후보임. 세 시안의 서로 다른 구조를 모두 제품화하는 뜻은 아님
- 카드 모서리·테두리·그림자 차이는 공통 구조 확정 후 필요성이 있으면 소수 토큰으로만 검토
- 우선 기본 디자인 하나를 완성하고, 색상 3종 적용·대비 검증 후 선택 기능을 추가하는 순서 권장
- 테마별로 앱 화면/팝업/선택기/애니메이션을 따로 구현하는 방향은 이번 범위에는 비추천
- 검증 조합: 앱 테마 × 달력 테마 × 시간대별 배경 × 지원 화면/언어 범위
  초기에는 앱 테마 선택만 적용하고 동적 배경은 뒤 단계로 분리하는 방안 검토
- 사용자 선택 저장·재실행 유지·미리보기·기본값·기존 사용자 설정 보존을 함께 설계
- 이 항목은 판단/설계 후보이며, 앱 전체 3종 테마 구현은 아직 확정하지 않음

■ 9. 전체 화면 전수 목록·완료 관리
- 화면 파일명 목록만으로 완료 판단하지 않음: 한 파일 안의 여러 창·중첩 창·상태별 분기도 각각 조사
- 조사 대상: lib/screens, lib/widgets, main.dart, services의 UI 호출, native Kotlin·XML·알림/위젯,
  외부 SDK·시스템 화면의 진입/복귀, 앱 범위에 연결된 웹 화면
- 진입 방식 조사: 탭·페이지 이동·showDialog·바텀시트·오버레이·선택기·알림/위젯 진입
- 상태 조사: 신규/기존 사용자·추가/수정·빈 데이터·로드 실패·권한 거부·백업 확인/복원/중단,
  일정관리 팝업·수면/회복·공유 중지·광고 동의/재설정·언어/국가별 조건부 표시
- 현재 작업은 Android 앱 전체 개선임. iOS 검토 당시 제외한 일정관리·수면/회복도 이번 목록에 포함
- 각 항목 필드: ID / 화면·창 이름 / 진입 경로 / 호출 파일·함수 / 구현 주체 / 현재 UI / 적용 규칙 /
  유지 요소 / 변경 요소 / 조건·상태 / 구현 상태 / 디자인 확인 / 기능 검사 / 실기기 증거 / 잔여
- 상태는 미조사·목록 확인·설계 확정·적용·검증·완료·외부 제약 등으로 구분
- 같은 공통 창을 여러 화면에서 사용하는 경우, 공통 창 ID와 모든 사용처를 연결하고 사용처별 확인
- “100% 적용”은 앱 소유 대상의 미적용/누락이 없고, 외부 화면은 허용 범위·제약·진입/복귀 검증이 기록된 상태
  정적 목록 수만으로 실기기 100% 검증을 주장하지 않음
- 실제 전수 목록은 다음 착수 단계에서 별도 원장으로 작성. 이 문서는 목록 작성 기준이며 완료 원장이 아님

■ 10. 확정 방향·외부 화면 처리
- 세이지의 차분한 형태·여백·카드 방향을 기본으로 하되 요소별 취향을 따로 확정
- 기존 고정 알람 시간 선택기 선호를 보존: AlarmTimePicker / TappableNumberPicker
  근거: lib/widgets/alarm_time_editor.dart, onboarding_screen.dart·settings_tab.dart의 사용처
- 시안의 숫자 입력형 시간 선택기로 일괄 교체하지 않음
- 년월·날짜·기간 선택기는 별도 검토하되 공통 글자·버튼·표면·닫기 규칙으로 연결
- 앱 색상 3종은 공통 구조 하나의 토큰 변형을 기본안으로 검토. 테마별로 Back/팝업 구조를 달리하지 않음
- 유럽 광고 동의는 현재 Google UMP SDK 화면임: ad_consent_service.dart의 ConsentForm 호출
  AdMob 메시지에서 제공하는 설정 범위를 확인하고, 앱 진입 버튼·안내·열기/복귀는 공통 UI로 정비
  SDK 화면 자체를 임의 Flutter 창으로 대체할 수 있다고 가정하지 않음. 수정 가능한 범위와 제약을 원장에 명시
- Android 권한창·설정·파일 선택기·공유 시트도 전체 사용자 흐름 목록에 포함
  시스템 소유 UI는 직접 재디자인 대상과 구분하고, 앱 측 연결·여백·복귀·표시 결과를 검증
- 공식 UMP 안내: https://developers.google.com/admob/flutter/privacy
