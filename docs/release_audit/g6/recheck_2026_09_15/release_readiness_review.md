# 교대시계 현재 코드 출시 적합성 재검토

작성: 2026-09-15
대상: `dev`, `8354ad466a2b58b23612c134c9a68bc2fbea2f6d`, `1.0.23+25`, DB v24
검토 방식: 현재 코드·기존 검토 기록·바탕화면 테스트 문서 대조, 기존 자동 테스트 실행, 독립 진단 테스트. 제품 코드는 변경하지 않았다.

## 1. 결론

**현재 상태에서 일반 사용자 대상 출시 승인은 보류하는 것이 맞다.**

이전 작업으로 DB 이관, 알람 생성 규칙, 개별 예외, 친구 공유 상태, 복원 절차가 상당히 정리됐다. 기존 Flutter 259개와 Android 75개 테스트도 이번 검토에서 모두 통과했다. 따라서 기존 개선을 무효로 보거나 처음부터 다시 만들 필요는 없다.

그러나 다음 세 가지 코드 문제는 출시 전에 고치는 편이 맞다.

1. 근무 일괄 변경 중 시스템 뒤로가기로 진행창을 닫으면, 작업 완료 시 다른 화면을 잘못 닫을 수 있다.
2. 복원 후 재시작 직전 새 알람이 시작되는 경우를 막지 못해, 새로 울리기 시작한 알람을 프로세스 종료로 끊을 수 있다.
3. 스누즈 대기 중 복원하면, 재울림의 오버레이 타이머가 복원 전 지속시간을 무시하여 알람을 일찍 끌 수 있다.

또한 **알람 소리를 백그라운드에서 지속시키는 구조의 실기기 검증이 빠져 있다.** 예약 시각에 알람이 한 번 시작되는 것과 설정한 시간 동안 끝까지 울리는 것은 별도 보장이다.

바탕화면의 11개 항목은 유용한 기본 점검이다. 하지만 **그것만 모두 통과하면 출시해도 된다는 결론은 성립하지 않는다.** 아래 보완 항목을 합쳐야 한다. 특히 “두 AI 리뷰로 절전·권한·복원 중단 테스트를 대신했다”는 근거는 충분하지 않다.

이 보고서는 모든 기기에서 모든 버그가 없다는 증명이 아니다. 코드로 확인된 문제와 실제 기기에서만 확인 가능한 위험을 구분한 출시 판단 자료다.

## 3. 현재 코드에서 추가 확인한 문제

등급은 피해와 발생 조건을 함께 고려했다. “코드 확인”은 실기기에서 직접 재현했다는 뜻이 아니다.

### AUD-01 — 높음: 일괄 변경 진행 중 뒤로가기로 화면이 잘못 닫힘

- 위치: `lib/screens/calendar_tab.dart:4274`, `:4308`, `:4325`.
- 일괄 변경의 진행창은 `barrierDismissible: false`만 설정되어 있다. 이는 배경 터치를 막지만 시스템 뒤로가기를 막지 않는다. `PopScope(canPop: false)`가 없다.
- 사용자가 날짜를 여러 개 선택하여 근무를 바꾼 뒤 로딩 중 뒤로가기를 누르면 진행창이 먼저 닫힌다. 비동기 저장은 계속된다. 완료·오류 처리의 무조건적인 `Navigator.pop(context)`는 당시 맨 위에 있는 다른 route를 닫게 된다. 메인 route가 대상이면 빈 화면이 될 수 있다.
- 최근 Q-02 수정은 “시트를 먼저 닫는다”는 순서 문제를 해결했지만 이 별도 종료 경로는 남았다.
- 검증: 실제 Flutter의 동일한 `showDialog` 설정으로 시스템 back을 전달했을 때 진행창이 닫히는 것을 진단 테스트에서 확인했다. 전체 CalendarTab을 조작한 실기기 E2E 재현은 아니다.
- 조치: 진행창의 뒤로가기를 막고, 작업이 소유한 route만 정확히 닫는다. 작업 중복 실행도 막는다. 성공·예외 양쪽에서 확인한다.
- 추가 테스트: 테스트 10에 “로딩 중 시스템 뒤로가기 여러 번 → 저장 완료 → 달력 정상, 다른 날짜 편집 가능”을 넣는다.

### AUD-02 — 높음: 복원 재시작 직전 시작된 알람을 끊음

- 위치: `lib/services/app_restart.dart:13`, `android/app/src/main/kotlin/com/hwani1103/shiftbell/MainActivity.kt:630`.
- Dart에서 마지막 `isAlarmRingingLive` 확인 후 600ms 기다린다. Native 재시작 처리도 300ms 뒤 실행되며, 그 직전에 알람 상태를 다시 확인하지 않는다. 마지막 확인부터 실제 종료까지 약 900ms와 스케줄링 지연의 틈이 있다.
- 그 사이 다음 알람이 수신되면 소리가 시작되지만 `Runtime.getRuntime().exit(0)`이 프로세스를 끝내 함께 끊는다. 상태 조회 채널이 실패해도 현재 함수는 `false`로 처리하여 재시작한다.
- 검증: 실제 `restartAppWhenNoAlarmRinging()`을 호출하고 최초 확인 100ms 뒤 울림 상태가 바뀌는 조건을 주입했다. **울림 상태인데도 restartApp 채널을 호출함**을 확인했다. 상태 조회 예외도 재시작으로 이어졌다. OS의 실제 프로세스 종료까지 실행한 테스트는 아니다.
- 조치: Native의 실제 종료 직전에 울림 시작·종료 상태와 함께 판단하고, 새 울림이 시작되면 종료를 보류한다. 조회 실패를 “울림 없음”으로 취급하지 않는다. 단순히 Dart에서 한 번 더 검사하는 것만으로는 최종 확인과 종료 사이의 경쟁을 없애지 못한다.
- 추가 테스트: 이미 울리는 중 복원 외에 “복원 완료·재시작 경계에 다음 알람 도착”을 실패 주입으로 검증한다.

### AUD-03 — 높음: 스누즈 복원 후 오버레이가 지속시간을 짧게 적용

- 위치: `CustomAlarmReceiver.kt:240`, `AlarmOverlayService.kt:174`, `:203`, `:232`, `:245` (이하 Kotlin 경로는 `android/app/src/main/kotlin/com/hwani1103/shiftbell/`).
- `CustomAlarmReceiver`와 `AlarmPlayer`는 `RestoreGate.ringSnapshot`의 복원 전 지속시간·소리를 사용한다. 반면 오버레이는 `loadAlarmInfo()`에서 현재 DB의 `alarm_types.duration`을 다시 읽어 자체 종료 타이머를 건다.
- 예: 지속시간 10분인 알람을 스누즈 → 같은 타입 ID의 지속시간이 1분인 백업을 복원 → 잠금 해제 상태에서 스누즈 재울림. Native 종료 예약은 10분이지만 오버레이의 1분 타이머가 같은 회차를 먼저 종료할 수 있다. 타입이 백업에 없으면 기본 3분으로 짧아질 수도 있다.
- 검증: 두 설정 조회 경로와 오버레이의 `claimRingEnd`→종료 경로를 코드로 확인. 실제 소리 재현은 미실행.
- 조치: 오버레이도 같은 스냅샷/회차의 확정된 종료 시각을 사용한다. 화면별로 종료 기준을 다시 계산하지 않는 편이 안전하다.
- 추가 테스트: 기존 통합 계획 C4의 **스누즈 후 다른 소리·지속시간 백업 복원**을 필수 목록에 넣는다. 바탕화면 테스트 8만으로는 이 경로를 통과하지 않는다.

### AUD-04 — 높음·실기기 게이트: 백그라운드 울림 지속 보장이 약함

- 위치: `CustomAlarmReceiver.kt:148`, `:163`, `:201`, `:299`, `AlarmOverlayService.kt:73`, `AndroidManifest.xml`.
- 소리는 receiver가 싱글턴 `AlarmPlayer`로 시작한다. 자체 재생용 foreground service가 없고, 오버레이도 일반 `startService`이다. foreground service 권한을 선언한 것만으로 서비스가 foreground가 되지는 않는다.
- 잠금 해제·오버레이 미허용 상태에서 알림으로만 제어하고 앱을 배경에 두거나, 알람 화면에서 홈으로 나간 경우에 재생을 유지할 활성 컴포넌트가 약해진다. receiver의 화면 깨우기 lock은 10초뿐이다.
- 이것만으로 모든 기기에서 소리가 끊긴다고 단정할 수 없다. 다만 Android는 활성 컴포넌트가 없는 프로세스를 회수할 수 있으며 일반 알림은 foreground service와 동일한 생명주기 보장이 아니다. [Android 공식 프로세스 생명주기 설명](https://developer.android.com/guide/components/activities/process-lifecycle)
- 기존 통합 계획의 H03과 연결되는 **미해결 신뢰성 위험**이다. 새로 발견한 확정 크래시와 같은 종류로 세지 않았다.
- 출시 조건: 충전 분리·기본 배터리 제한·잠금/해제·오버레이 허용/거부에서 5분 이상 끝까지 울림, 홈 이동 후 지속·자동 종료, 소리와 실제 PID 생존을 확인한다. 불안정하면 재생 책임을 적절한 foreground service로 옮기는 설계가 필요하다. 한 번 성공했다고 모든 OEM의 안정성이 증명되지는 않는다.

### AUD-05 — 중간: 자정 이후 컨디션 계산에 전날 기준이 남음

- 위치: `lib/providers/condition_provider.dart:68`, `:79`, `lib/providers/sleep_condition_provider.dart:158`, `:185`, `lib/screens/condition_tab.dart:124`.
- `todayConditionResultProvider`와 최근 7일 OT 조회는 생성 시 `DateTime.now()`를 사용하지만 날짜 변경을 구독하지 않는다. 근무/근무시간/OT가 바뀌지 않으면 일반 Provider 캐시가 남는다.
- 컨디션 화면으로 복귀할 때는 수면 목록만 새로 읽는다. 그 결과 수면 기반 계산은 새로 돌면서도 `baseResult`와 OT 범위는 전날 값일 수 있다. 앱을 밤부터 다음 날까지 살려 둔 교대근무 사용자에게 실제로 관련 있는 조건이다.
- 검증: 의존성과 lifecycle 갱신 경로를 확인. 실제 자정 통과는 미실행.
- 조치: 공통 “현재 날짜” 상태를 두어 자정·앱 재개 시 갱신하고, 오늘 기준 계산과 기간 조회가 이를 구독하게 한다.
- 추가 테스트: 서로 다른 근무가 이어지는 날짜의 23:59→00:01, 다음 날 앱 재개. 근무를 수정하거나 프로세스를 새로 시작하지 않고 오늘 결과가 바뀌는지 본다.

### AUD-06 — 중간: 미리듣기와 실제 알람이 시스템 음량 복원을 서로 덮어씀

- 위치: `MainActivity.kt:1124`, `:1139`, `:1171`, `:1199`, `AlarmPlayer.kt:194`, `:208`, `:452`.
- 두 객체가 각자의 `originalAlarmVolume`을 저장하고 같은 `STREAM_ALARM`을 변경한다. 상호 조정은 없다.
- 예: 시스템 알람 볼륨 0에서 미리듣기가 50%로 올림 → 실제 알람 도착, AlarmPlayer는 그 50%를 원래 값으로 기억 → 미리듣기 종료가 0으로 복구하여 실제 알람까지 작아지거나 무음 → 실제 알람 종료는 50%를 복구하여 사용자 설정도 바뀜.
- 코드상 공유 자원 충돌을 확인했다. 음량 단계·실제 들림은 기기에서 확인해야 한다.
- 조치: 실제 울림과 미리듣기의 음량 소유·복원을 한곳에서 관리하거나, 실제 울림 전에 미리듣기를 안전하게 정리한다.
- 테스트 11의 “정상 재생 완료 후 복원”만으로는 잡히지 않는다. 미리듣기 중 실제 알람 도착을 추가한다. 또한 `onDestroy`는 프로세스 회수 시 보장되지 않아 “스와이프 종료하면 반드시 복구됨”이라는 합격 기준은 과하다. [Android 생명주기 설명](https://developer.android.com/guide/components/activities/process-lifecycle)

### AUD-07 — 중간·화면 조건: 광고 요청 폭과 실제 표시 폭이 다름

- 위치: `lib/services/ad_service.dart:70`, `:91`, `lib/main.dart:314`, `:371`, `lib/widgets/banner_ad_slot.dart:119`.
- 광고 크기는 기기 전체 logical width로 한 번 계산하지만 앱 내용은 최대 500dp로 제한한다. 600/840dp 화면에서는 요청 폭이 실제 슬롯 폭보다 커진다. 접기/펼치기·멀티윈도우로 크기가 달라져도 재계산하지 않는다.
- 코드상 폭 불일치는 확정이다. 광고가 안 보이거나 잘리는 구체 결과는 SDK·플랫폼뷰에서 확인이 필요하다. “세로 고정이므로 폭은 바뀌지 않는다”는 주석은 폴더블·멀티윈도우를 포함하지 못한다.
- 조치: 실제 광고 슬롯의 layout constraint로 크기를 요청하고 폭 변경 시 다시 만든다.
- 추가 테스트: 기본 폰 360dp와 넓은 화면 하나에서 확인. 360/600/840×모든 글꼴×모든 방향의 전수 조합까지 필수로 돌릴 필요는 없다.

### AUD-08 — 낮음·개발 품질: 전체 분석 명령이 빨간 상태

- 오래된 재현 코드가 현재 SDK에서 오류를 내고 정상 분석 결과를 가린다. 사용 중인 테스트와 보관용 예제를 명확히 나누어 기본 분석이 의미 있는 gate가 되게 해야 한다.
- 대부분의 나머지 항목은 unused/deprecated/style 성격이다. 632라는 숫자 전체를 출시 차단 버그 개수로 해석하면 안 된다.
- 웹 전용 URI 오류는 실제 웹 빌드 결과와 분리하여 다룬다. **일반 JavaScript 웹 release 빌드는 성공했다.** WebAssembly 사전 검사에서는 `dart:html`·`dart:js_util`·일부 플러그인 호환성 경고가 나왔다. 현재 일반 웹 배포를 막는다고 판정하지 않는다. Android 단위 테스트 컴파일과 기존 Flutter 테스트도 통과했다.

## 4. 이전 개선과 위험 수용의 재평가

- **DB**: Device Protected 경로, v24 스키마/이관 asset, 실패 시 시작 화면, 비파괴 repair, 프리셋 보강과 양쪽 자동 테스트는 좋은 개선이다. 과거 DB 경로 분리 문제를 현재의 미수정 문제처럼 다시 지적하지 않았다.
- **알람**: 회차 번호, 공통 예약 경로, 예외 테이블, Dart/Kotlin 공통 fixture는 유지보수에 도움이 된다. 하지만 화면 타이머·프로세스 종료·시스템 음량까지 완전히 통합된 것은 아니다.
- **복원**: 전체 화면 입력 차단, 중단 작업 기록, 이월 ID와 epoch, 원본 사본, 미래 custom 재예약은 진전이다. 위 AUD-02·03 때문에 “울림 중 복원 완전 해결”이라고 판정할 수는 없다.
- **친구 공유**: active/stop_pending, 서버 미확인과 삭제의 구분, 로컬 캐시 유지, 이름 길이 보정은 확인했다. 서버 상태·네트워크 큐까지 mock 테스트만으로 확정할 수 없다.
- **R-01/X-01**: 구버전 불규칙 근무의 개별 삭제·타입 변경이 업데이트 직후 1회 원복될 수 있는 사항은 기존 문서에 **사용자 수용, 안내 안 함**으로 기록되어 있다. 이번 보고서는 이를 신규 미수정 버그로 다시 세거나 수용 결정을 변경하지 않는다. 다만 “업데이트 시 모든 개별 설정 보존”이라는 일반 합격 기준과는 구분해야 한다.
- 앞선 조사 중 발견한 `changeShiftWithAlarms`의 실패 안내 누락은 현재 CalendarTab의 미사용 `_changeShift` 경로에 연결되어 있었다. 사용자 경로를 확인한 뒤 **실사용 결함 목록에서 제외**했다.

### 문서 설명에서 반드시 바로잡을 것

1. **dev APK 업데이트와 스토어 업데이트의 차이가 설치 버튼 주체 하나뿐이라는 설명은 과장이다.** 코드/DB/브로드캐스트 검증에는 유용하지만 package, flavor 설정, 서명, AAB split, 실제 광고·Analytics 설정이 다르다. 최종 prod AAB는 테스트 계정으로 Play 내부 테스트 트랙에서 설치·업데이트 확인해야 한다. 이는 일반 사용자 정식 출시가 아니다. 로컬 prod APK로 현재 실사용 앱을 지우거나 덮으라는 뜻도 아니다. [Play 내부 테스트 공식 안내](https://support.google.com/googleplay/android-developer/answer/9845334?hl=en)
2. **“권한·Doze·복원 중단은 AI 리뷰로 대체”를 삭제한다.** OS 생명주기와 전달 지연은 순수 로직 테스트로 대신할 수 없다.
3. **최근 앱 스와이프는 프로세스 종료 증거가 아니다.** 통합 계획 C2/C5도 동일한 문제가 있다. task 제거와 PID 소멸을 구분해야 한다. 중단 시험은 테스트 전용 환경에서 단계별 중단과 실제 PID 종료를 기록한다. 앱 강제 중지로 OS 예약까지 제거했다면 이후 알람 미전달과 앱 결함을 혼동하지 않는다.
4. **통합 계획 D5의 “재설치 뒤 옛 링크가 불러올 수 없음”은 현재 구현과 맞지 않는다.** 공유 중지 없이 재설치하면 옛 서버 문서는 남을 수 있다. `fetchByOwnerIdDetailed`와 rules에는 재설치 감지나 TTL이 없다. 개인정보 안내와 도움말도 옛 공유 내용을 회수할 수 없다고 설명한다. “중지 후 삭제 확인”과 “중지 없이 재설치한 잔존 데이터”를 별도 기대값으로 써야 한다.
5. **통합 계획 E1의 빠진 ID로 빌드 성공 후 빈 광고 확인은 현재 빌드 가드와 충돌한다.** 누락/테스트 ID는 prod release 빌드 실패가 올바른 결과다. Flutter CLI에 Gradle `-P`를 직접 붙이는 예시 대신 바탕화면 문서처럼 사용자 Gradle properties로 주입하는 명령을 사용한다.
6. **정확한 알람 권한 거부 테스트는 기기별 적용 가능성을 확인한다.** 현재 Manifest는 `USE_EXACT_ALARM`과 `SCHEDULE_EXACT_ALARM`을 함께 선언한다. 전자는 자동 부여되고 사용자가 취소할 수 없는 권한이므로, 모든 OS에서 설정 화면으로 동일하게 거부 상태를 만들 수 있다고 가정하지 않는다. 해당 기기에서 재현 불가하면 N/A 사유와 다른 API 환경/실패 주입 결과를 남긴다. [Android 알람 권한 설명](https://developer.android.com/develop/background-work/services/alarms)
7. **충전 연결한 20분 대기를 절전 테스트로 세지 않는다.** 기본 전달 확인에는 충분하지만 Doze 조건과 다르다. 일정 알림과 기상 알람은 사용하는 예약 API도 다르므로 ±1분 합격 기준을 무조건 공유하지 않는다. [Android 알람 동작 설명](https://developer.android.com/develop/background-work/services/alarms)

### 테스트 담당과 시간

- 한 대의 주력 삼성 폰에서 dev 앱으로 대부분 수행할 수 있다. 하룻밤 검증에 자정·절전·수면 후보 확인을 합친다.
- 날짜/시간대 조작·프로세스 중단·권한 실패 주입은 실사용 알람이 없는 에뮬레이터 또는 전용 기기로 분리한다.
- 친구 공유 A/B는 본인 테스트 계정 두 개와 보조 에뮬레이터/브라우저로 검증할 수 있다. 다른 사람에게 메시지를 보낼 필요가 없다.
- 최소한 두 번째 Android API/OEM 환경에서 알람의 설치·잠금·지속·종료를 짧게 확인하면 한 기기 의존을 줄일 수 있다. 모든 제조사 구매나 전수 검사를 뜻하지 않는다.
- 대략 능동 작업 반나절~하루와 하룻밤 방치가 현실적이다. 실패 수정과 재검증 시간은 별도다. “2~3시간에 전부 출시 검증 완료”로 잡기에는 변경 범위가 크다.

### 줄이거나 빼도 되는 것

- **스토어 1.0.22의 알려진 버그를 현재 실사용 앱에서 일부러 재현하는 선택 절차**: 출시 gate에 불필요하다. 새 버전의 기대 동작과 업데이트 보존 검증에 시간을 쓴다.
- 같은 조건의 끄기/5분 스누즈를 테스트 1과 4에서 기계적으로 반복하는 부분: 합쳐도 된다. 업데이트/잠금/오버레이 조건이 달라지면 별도 검증 가치는 있다.
- 근무명 쉼표·예약어·중복 등 이미 fixture로 확인되는 모든 입력 조합을 모든 기기에서 반복하는 것: 대표 UI 오류 안내 한 번과 자동 테스트로 축소한다.
- 화면 크기×글꼴×방향 전수 조합: 기본 작은 폭+큰 글꼴, 넓은 폭 하나로 우선 축소한다. 주 화면의 세로 고정 특성도 반영한다.
- 10일 창이 들어올 때까지 실제 11일을 기다리는 것: 계산은 자동 fixture와 전용 에뮬레이터 날짜 이동으로 확인하고, 실제 자정 트리거는 하룻밤 검사한다.
- 광고 no-fill일 때 “Test Ad가 뜰 때까지” 무한 반복하는 것: 로드 오류/ID/레이아웃을 기록하고 원인을 구분한다. 최종 prod 배포 설정 점검을 생략한다는 뜻은 아니다.

## 7. 코드 품질 총평과 출시 조건

| 영역 | 평가 |
|---|---|
| 데이터 이관/알람 계산 | 이전보다 견고함. 공통 fixture와 실제 SQLite·Kotlin 검증이 강점 |
| 알람 화면/프로세스/음량 | 출시 핵심 취약점. 같은 상태를 여러 컴포넌트가 각각 관리하면서 경계 조건이 남음 |
| 복원 | 절차와 복구 경로는 좋아졌으나 OS·DB·메모리 상태가 맞물리는 통합 검증이 부족 |
| 상태 갱신 | 근무/OT 변경 통지는 개선됐으나 날짜 변경과 일부 lifecycle 경로가 빠짐 |
| 자동 테스트 | 계산/이관 중심의 기반은 유효. OS 실제 전달·장시간 재생·복원 화면 흐름의 증거는 별도 필요 |
| 유지보수 | 큰 화면·Native 메인 파일, 복제된 타이머/음량 상태, 오래된 테스트 사본과 설명 충돌이 다음 회귀의 원인이 될 수 있음 |
| 출시 절차 | gate 문서가 비어 있고 최종 prod 파일·기기·Console 증거가 없어 아직 승인 단계가 아님 |

**권장 순서**

1. AUD-01·02·03을 수정하고 그 조건을 회귀 테스트로 남긴다. AUD-05·06도 이번 출시에서 처리하는 편을 권한다. 넓은 화면을 지원 범위에 포함하면 AUD-07을 해결한다.
2. AUD-04를 포함한 M2~M8을 최종 후보로 수행하고 결과를 기록한다. 자동 테스트 성공을 실기기 PASS로 옮겨 적지 않는다.
3. M1·M9를 완료한 **동일 prod 산출물**을 승인한다. 새로운 변경을 넣으면 영향받는 연결 경로를 다시 확인한다.
4. 그 뒤 소규모 단계적 출시를 진행한다. 이는 출시 전 검증을 대신하지 않는다. 업데이트 원격 안내 versionCode는 실제 배포 범위와 맞춘다.

요약하면, **전체적인 개선 방향과 자동 검증 기반은 좋다. 지금 남은 일은 무제한 전면 재검토가 아니라 확인된 알람·화면 경계 버그 수정과 빠진 실제 환경 검증이다. 현재 증거만으로 “그대로 출시해도 된다”는 판단은 권하지 않는다.**
