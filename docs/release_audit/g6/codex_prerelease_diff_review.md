- 작성: 2026-09-14. 검토 목적은 **1.0.22 사용자의 데이터·알람·설정이 업데이트 후 유지되는지** 확인하는 것이다.

- 이후: `404c830970bd736e9576ab6d81cf7e7a06267622` — 검토 대상 `1.0.23+25`, DB v24.

### 판정 읽는 법

**출시 승인 보류를 권고한다.** 전체 v18→v24 마이그레이션이 깨진다는 증거는 찾지 못했지만, 구버전 개별 알람 변경값의 승계와 덮어쓰기 복원에 해결할 문제가 남았다. 특히 X-01~X-03은 코드에서 직접 확인되는 경로다. X-04의 실제 경합 발생은 재현이 필요하다.

발견 사항은 **High 4건, Medium 7건, Low 1건, 운영 2건**이다. Critical로 확정한 항목은 없다. 빈도가 낮다는 이유로 데이터 손실이나 알람 제어 실패의 중요도를 낮추지는 않았다. 이 개수는 독립 원인별 분류이며, 서로 결합하는 항목도 있다.

- **코드 확인**: 해당 조건에서 실행되는 분기·상태 변화가 소스에 명시되어 있다. 실기기에서 재현했다는 뜻은 아니다.
- **추정**: OS 전달 순서, 동시 실행 타이밍, SDK의 실제 수집·표시 결과가 추가로 필요하다.
- **직접 회귀**: 같은 기존 데이터를 사용하던 1.0.22보다 동작이 달라진다.
- **신규 경로 결함**: 1.0.22에는 기능이 없었지만, 업데이트 사용자의 기존 데이터를 이 기능이 변경한다. 순수 업데이트 직후의 회귀와 구분했다.

아래에서 `N/`는 `android/app/src/main/kotlin/com/hwani1103/shiftbell/`의 약칭이다. 별도 표기가 없으면 파일·줄 번호는 **404c830** 기준이다.

### 2.1 중요한 재현 경로와 범위 구분

**X-01: P1 도입과 기존 예외 보존은 서로 다른 작업이다.** 새 버전에서 `updateAlarmTypeWithOverride()`와 삭제 시 override 기록이 들어간 것은 확인했다(`lib/services/database_service.dart:876`, `:908`, `:561`). 하지만 이 코드는 업데이트 전에 이미 수행한 변경에는 실행되지 않는다. v24 SQL에는 기존 행을 읽어 override를 만드는 DML이 없다. 새 버전에서 알람 A/B를 바꾸는 실기기 메모의 테스트 5는 이 승계를 확인하지 못한다.

또한 `N/AlarmRefreshEngine.kt:81`, `:93`의 diff identity에 `alarmTypeId`가 포함된다. 따라서 기존 무음 타입과 템플릿 타입이 다르면 단순 재예약이 아니라 기존 행 제거와 새 행 생성 대상이 된다.

불규칙 자동 생성 자체는 v4 D1/D1-a로 승인된 동작 변경이다. 기존 사용자가 먼 미래에 배정했으나 알람은 아직 없던 날짜에 이제 알람이 준비되는 것은 오류가 아니다. 다만 릴리스 노트(`lib/l10n/app_ko.arb:516`, `app_en.arb:503`)에는 탭 추가만 있고 이 정책 변경 안내가 없다. 삭제/무음 승계 수정과 함께 사용자에게 바뀐 동작을 설명해야 한다. 앱 미실행 시에도 생성되므로 첫 실행 팝업만으로 첫 울림 전에 모두 알릴 수 있다고 가정하지 않는다.

**X-02: 데이터 교체가 성공해도 화면 상태가 옛 데이터일 수 있다.** `MainScreen`은 `_tabs[_currentIndex]` 한 탭만 트리에 올린다. 복원 중 다른 탭으로 이동 → SettingsTab dispose → 작업 자체는 계속됨 → 복원 완료 후 화면의 mounted 검사에서 반환 → 재시작 생략이라는 경로가 성립한다. 네이티브 `RestoreGate`는 Dart의 `DatabaseService` 쓰기를 자동으로 막는 DB 락이 아니다. 복원 직후 옛 `ScheduleNotifier` 값으로 날짜 하나를 고치는 것만으로도 새 DB의 다른 설정을 덮어쓸 수 있다.

1. 복원에서 옛 예약을 취소한다.

## 4. 보지 못한 범위(한계)와 실기기 메모 검토

### 4.1 이번 감사의 한계

1. **실행 증거가 없다.** 모든 재현 절차는 코드로 도출한 제안이다. X-04/X-05의 실제 동시 실행 순서, 프로세스 생존, OS 알람·알림 전달, MediaStore 권한/제조사 동작은 실기기/실패 주입으로 확인해야 한다.
2. **APK/AAB와 SHA의 대응을 확인하지 않았다.** 메모의 두 APK 경로가 존재하고 올바르게 빌드되었다는 주장, 실제 스토어 바이너리가 ca82d69와 일치한다는 주장은 사용자 기준으로 받아들였다. 파일 해시·서명 인증서·merged Manifest·최종 자산·실제 minSdk/ABI·난독화 결과를 확인하지 않았다. 버전 문자열만 같아도 같은 소스라는 증거가 되지는 않는다.
3. **DB의 실제 사용자 분포를 모른다.** 정상 v18→v24 SQL은 검토했지만, v18 미만 모든 역사 fixture를 이번에 재생성/실행하지 않았다. 이미 버전만 최신으로 stamp된 DB, 잘못된 friends 구조, 컬럼 자료형/제약 손상, 저장공간 부족·WAL 실패는 자동 repair가 모두 고치는 범위가 아니다. REPAIR-REJECT의 기존 사용자 결정도 유지했다.
4. **변경 전체를 동일 깊이로 전수 감사한 것은 아니다.** 업데이트 경계와 v4 수정 경로를 우선했다. 대규모 신규 일정 UI, 수면/컨디션 알고리즘 전체, SVG/이미지 자산, 웹 화면 전체, 화면별 스크롤/접근성/번역 전체 및 모든 사용자 조작 조합은 미검토 또는 부분 확인이다. 읽은 테스트 소스/과거 PASS 문서도 실행 결과로 간주하지 않는다.
5. **시간대/DST는 별도 잔여 위험이다.** 저장 시 Locale.US 고정과 날짜별 근무 계산의 Julian day 사용은 확인했지만, 모든 날짜 파싱 실패·DST의 존재하지 않는/두 번 존재하는 시각을 양쪽 런타임에서 대조 실행하지 않았다. 예를 들어 일정 trigger는 Dart와 Kotlin 모두 자정에서 분을 더하는 구조다. 이 구조의 현지 벽시계 의미는 DST 날짜에서 별도 확인해야 한다. 한국 표준시만으로 일반화하지 않는다.
6. **외부 서비스 실제 상태를 확인하지 않았다.** Firebase 앱 등록/서명 연계/API 제한, 운영 rules, 익명 Auth·오프라인 write의 늦은 ACK, Analytics 실제 이벤트, 광고 계정/동의 설정, Play 배포·권한·데이터 보안 양식은 미확인이다. 개인정보 문구 검토는 코드와 표현의 대응 검토이며 법적 적합성 판단이 아니다.
7. **문서 모순은 제품 동작으로 판정하지 않았다.** v4의 계획, G4 인계의 “Guard 읽기 전용”, device_test_plan의 “백업 파일 1개” 등을 그대로 사실로 인용하지 않고 실제 호출을 대조했다. 금지된 Claude 독립 리뷰와의 cross check는 아직 수행하지 않았다.

#### C. 줄이거나 실기기에서 빼도 되는 부분

- **스토어 실사용 앱에서 옛 버그를 재현하는 선택 절차**는 생략해도 된다. 비교 기준의 old dev 설치에서 충분히 준비할 수 있고, 실사용 알람 값을 바꾸는 것은 이번 검증에 필수가 아니다.
- **DB v1~v23 모든 버전 및 SQL 중간 실패를 삼성 폰으로 반복**할 필요는 없다. 버전별 스키마·기대 데이터·롤백은 개발 측 fixture/자동 검증에 적합하다. 실제 폰에서는 v18 업데이트·Native 선행·잠금 해제 전 핵심 경로를 남긴다. 이번에는 그 자동 검증을 새로 실행하지 않았다.
- **쉼표·예약어·중복·맞교환을 모든 화면/언어에서 반복**하는 것은 축소 가능하다. 기존 자동 검증과 코드 대조를 근거로 대표 입력/rename 1회 수준이면 된다. 단 X-11의 구버전 허용 데이터와 백업 검증은 별도다.
- **새 알람의 기본 끄기·스누즈를 테스트 1과 4에서 같은 조건으로 여러 번 반복**할 필요는 없다. 테스트 1에서는 업데이트 직후, 테스트 4에서는 홈 이동/오버레이/알림 버튼 등 다른 경로에 시간을 쓴다.
- **광고 ID 누락 조합 전부를 본인 폰에서 광고 노출로 확인**할 필요는 없다. 빌드 설정/최종 산출물 검사로 상당 부분 검증할 수 있다. 실제 prod 후보의 시작·배치·정상 구성 확인은 남긴다.
- **화면 폭·폰트 배율 전체 조합**은 이번 업데이트 회귀의 필수 전수 범위에서 줄일 수 있다. 사용자 기기의 기본/큰 글자에서 끄기·스누즈·복원 진행 UI가 가려지지 않는지만 우선 확인한다.
- **실사용 폰의 시스템 날짜/시간대 변경**은 피하는 것이 타당하다. 별도 기기/에뮬레이터로 이관하고 미실행 여부를 기록한다. 시간대 회귀까지 확인된 것으로 바꾸지는 않는다.

### 4.3 교차 대조와 출시 판단에 남길 기록

Claude와 비교할 때는 각 ID별로 **같은 SHA의 호출 경로, 구버전에서도 성립하는지, 실제 입력/타이밍 조건, 기존 방어 로직이 증상을 막는지**를 대조해야 한다. 특히 X-04/X-05는 추정 경합의 재현/반증 결과를 추가할 대상이다. 신규 복원 결함을 기존 사용자 모두에게 즉시 생기는 업데이트 회귀로 합산하지 않는다.

현재는 X-01~X-03 수정 판단, X-04/X-05 경합 해소/검증, X-06~X-09의 복원 완료·데이터 보존 조건 정리가 우선이다. 그 뒤 실제 시험한 산출물과 최종 배포 산출물을 연결해야 한다. 기본 7개 실기기 시험의 통과만으로 이 문서의 잔여 범위까지 PASS로 처리하지 않는다.
