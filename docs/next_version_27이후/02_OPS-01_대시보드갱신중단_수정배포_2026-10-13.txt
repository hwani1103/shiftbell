저장 실패 원인
- 마지막 이전 성공: 10/12 20:14 KST, run38241379756.
- 10/13 00:20/09:37 예약 실행은 Element at index 0 should not be an empty string 오류로 실패.
- Firestore SDK는 빈 map field name을 허용하지 않음. countryTrend는 GA4의 빈 국가명을 series의 키로 사용했고, batch.set에서 전체 저장이 중단됨.
- 같은 오류를 실제 SDK의 네트워크 없는 batch.set으로 재현. 빈 이벤트 키도 방어가 없던 경로를 함께 보완.
- 수정 후 실제 GA4 로그에서 countryDaily.country 빈 값 1행 확인. 국가·언어 추이, 국가 요약, 제조사 및 기간별 이벤트 요약에도 빈 차원값이 관측됨.
- 과거 실패 당시 원시 payload는 보존되지 않았으므로 그 시점의 행 값을 직접 재확인한 것은 아님. 코드 재현 및 복구 실행의 실제 countryDaily 관측을 근거로 저장 중단 경로를 확인함.

수집량/실행 공백 판단
- 기존 성공 수집 약5.7초, 실패 약4~6초, 최초 복구5622ms/최종 복구12921ms. 8~13시간 수집에 걸린 문제가 아님.
- cron은 원래3시간 간격이었으나 실제 예약 실행 사이에 긴 공백이 존재. 예: 10/13 00:20→09:37. 누락/지연 자체의 GitHub 내부 원인은 미확정.
- 과거8~9시간 공백 모두가 같은 저장 오류였다고 단정하지 않음. 저장 실패와 예약 실행 지연/누락은 별개.
- GitHub schedule은 지연/누락 가능: https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule

구현
- 국가/언어/제조사 빈 값은 (missing)(미제공)으로 정규화하고 해당 수치를 보존. 기존 GA4 (not set)(확인 불가)와 분리하여 중복 사용자 수를 합산하거나 동일 선택키로 충돌하지 않음.
- 이름 없는 이벤트는 실제 기능으로 집계하지 않음. 리포트 경로/열/행 수는 summary.dataQuality 및 로그로 관측. 사용자 원시 정보/인증키는 로그에 남기지 않음.
- Firestore 저장 전 빈 필드명을 검사하여 이후 오류는 정확한 문서 경로를 제공. 기존 단일 배치의 원자적 저장 유지.
- 매시간17분 실행(17 * * * *)으로 누락·실패 구간을 따라잡음. 성공한3시간 구간은 GA4 호출 전 건너뜀. 정상 수집은 하루8개 구간 유지. 실패한 실행은 성공 구간으로 기록되지 않음.
- 웹6시간 이상 미갱신 시 집계 지연을 표시(종전36시간)하고 안내를 새 방식에 맞춤.
- GitHub 예약 자체는 계속 best effort이므로 정시 실행/향후 누락0건을 보장하지 않음. 다음 실제 자동 예약 발화는 미래 관측 항목.
